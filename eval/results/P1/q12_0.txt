**最常见的原因是：加索引后，执行计划改成了索引扫描，而大量回表访问让查询更慢。**

普通索引扫描先找到行的位置，再读取表里的数据。假设一张表有 1000 万行，条件命中 300 万行，而且这些行分散在大量数据页中，走索引就要同时支付“扫描索引＋访问表”的成本；顺序扫描可以连续读取数据页，效率更高。[PostgreSQL 官方说明](https://www.postgresql.org/docs/current/using-explain.html)

重点排查这几种情况：

- **条件命中太多行。** 状态、类型等字段的某个值占比很高，索引筛选效果弱。
- **优化器低估了命中行数。** 统计信息过旧、数据分布倾斜或多个条件相关，会让优化器选中实际成本更高的计划。[统计信息文档](https://www.postgresql.org/docs/current/planner-stats.html)
- **索引只覆盖部分查询需求。** 还要回表取列、过滤其他条件、排序；复杂查询还可能改用执行次数很多的 `Nested Loop`。
- **前后测试的缓存和负载不同。** 同一个计划在缓存未预热、并发负载较高时，耗时也会增加。

先获取原查询的实际执行计划：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ... FROM your_table WHERE ...;
```

这里的 `ANALYZE` 会实际执行查询。重点看：

| 计划中的信息 | 排查方向 |
|---|---|
| `Index Scan`、`Bitmap Heap Scan` | 索引路径及表数据访问量 |
| 估计 `rows` 与 `actual rows` 相差很大 | 行数估计失准 |
| `Rows Removed by Filter` 很大 | 扫描了大量最终被过滤的行 |
| `Nested Loop` 内层 `loops` 很大 | 重复访问成本高 |
| `Buffers: shared read` 很多 | 数据页读取量大 |

保存这份计划后，更新统计信息再测一次：

```sql
ANALYZE your_table;
```

如果行数估计改善、计划随之改变且耗时下降，就能确认统计信息是主要原因。

把原 SQL、`CREATE INDEX` 语句和执行计划贴出来，就能进一步定位。**上述机制判断置信度高；具体主因目前置信度低，因为缺少执行计划和命中行数。**
