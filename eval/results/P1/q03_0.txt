**优先排查 I/O 等待、资源池排队和锁竞争。** 请求在等待时几乎不消耗 CPU，所以 CPU 只有 30%，接口 p99 仍然会涨到 800ms。

常见原因有：

| 原因 | 延迟上涨的机制 | 检查证据 |
|---|---|---|
| 数据库或下游服务变慢 | 慢查询、行锁、网络抖动、下游长尾增加 | 链路追踪中数据库、RPC 的耗时 |
| 线程池或连接池耗尽 | 请求等待工作线程、数据库连接、HTTP 连接 | 活跃数达到上限、队列长度和获取资源耗时增加 |
| 锁竞争 | 请求阻塞在互斥锁、共享缓存或串行逻辑上 | 线程栈大量停在相同锁或调用位置 |
| 局部 CPU 瓶颈 | 单个核心、事件循环或某个实例满载，整机平均值仍低 | 每核、每实例 CPU，以及热点线程 |
| GC 或运行时暂停 | 少数请求撞上暂停，尾延迟升高 | GC 暂停时间与延迟尖峰的时间对应 |
| 流量或请求结构变化 | 突发流量造成排队，重请求、缓存失效、重试放大负载 | 并发数、缓存命中率、重试率、慢请求分布 |

**最快的定位顺序：**

1. 对比上涨前后的 p50、p95、p99、QPS 和并发数：p50 稳定、p99 上涨时，重点找间歇性阻塞和少量慢请求。
2. 抽取接近 800ms 的请求，把耗时拆成：**入口排队 → 获取资源 → 数据库/下游 → 本地计算 → 响应发送**。
3. 对耗时增加的那一段，查池等待、锁等待、下游耗时或暂停记录。

还有一个常见遗漏：**确认监控的 CPU 统计范围与接口实际运行范围一致**，尤其是容器 CPU 配额、单实例热点和分钟平均值。
