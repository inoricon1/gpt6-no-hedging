**优先怀疑请求在等待：下游、数据库、连接池、锁或排队。** 这些等待会拉长响应时间，CPU 仍然可以保持在 30%。

常见原因按排查优先级排列：

| 原因 | 为什么会出现这个现象 | 重点看什么 |
|---|---|---|
| **下游服务变慢** | RPC、HTTP、Redis 等调用耗时上涨；超时和重试进一步放大延迟 | 各下游调用的 p99、超时率、重试次数 |
| **数据库变慢** | 慢查询、锁等待、磁盘读取让请求阻塞 | SQL 耗时、锁等待、执行计划、数据库 I/O 延迟 |
| **连接池或线程池耗尽** | 请求等待可用连接或工作线程，排队期间 CPU 消耗很低 | 获取连接耗时、活跃连接数、等待队列长度 |
| **锁竞争或串行执行** | 大量请求等待同一把锁，实际执行并发受限 | 线程栈、锁等待、事件循环延迟 |
| **局部 CPU 饱和或限流** | 单个核心、单个实例可能已满；容器也可能触发 CPU 配额限制 | 每核、每实例 CPU，以及容器 throttling 指标 |
| **GC、网络或存储抖动** | 少量请求遇到暂停、丢包重传、磁盘延迟，直接抬高尾延迟 | GC 暂停、TCP 重传、磁盘延迟，与慢请求时间对齐 |

**最快的定位方式是拆开那 800ms：**

1. **先看 p50、p95 和各实例 p99。** p50 稳定而 p99 上涨，优先查少量慢请求、热点和抖动；整体分位数一起上涨，优先查共同依赖和排队。
2. **拿慢请求的 trace，拆成“入口排队 → 应用执行 → 获取连接 → 下游调用”。** 哪段多出约 600ms，就沿着那段查。
3. **对齐变更和负载。** 看是否刚发布、流量或并发上涨、请求数据量变大、缓存命中率下降。下游变慢也会让连接占用更久，随后造成池耗尽和排队。

对“等待或局部瓶颈导致延迟”的判断置信度中等，具体原因需要慢请求分段耗时和资源等待指标来确定。
