**优先按“报表任务持续积累内存，约 10 分钟后触及内存上限”排查。** 最可疑的是结果集、聚合状态或导出缓冲随处理进度增长；其次是消费变慢导致队列堆积，以及任务重叠运行。

依据是三次故障都集中在报表时段，且内存持续爬升。排查重点应放在：**内存增长属于哪个进程、增长跟哪个处理阶段同步、这些内存被谁持有。**

下面的命令按 Linux / Kubernetes 环境给出，其他部署方式沿用同一排查顺序。

**先控制下一次故障，同时保留现场。**

如果报表与在线请求共用进程或容器，优先把报表移到独立 worker，并设置独立内存预算。短期可暂停一次调度，或缩小数据范围、将并发降到 1；跨实例运行的任务加互斥，重试加退避和次数限制。

临时扩容可以争取一次完整运行和采样的窗口，扩容量依据节点余量与任务峰值确定。按当前斜率，增加相当于原上限 20% 的空间，预计只会延后约 5 分钟触顶。

接着按下面顺序查。

**1. 确定触及的是哪个上限，以及谁执行了终止。**

先找到监控“60% → 100%”的原始查询，确认分子、分母和聚合方式：

- 分子：进程 RSS、容器总使用量、working set、运行时堆，还是节点已用内存。
- 分母：容器 limit、运行时最大堆，还是主机总内存。
- 聚合：逐实例曲线、最大值，还是多个副本平均值。

将百分比转为字节，逐实例查看故障前后的曲线。

Kubernetes 可先取：

```bash
kubectl describe pod <pod> -n <namespace>
kubectl get pod <pod> -n <namespace> -o yaml
kubectl logs <pod> -n <namespace> -c <container> --previous --timestamps
```

重点记录 `lastState.terminated`、`reason`、`exitCode`、终止时间、内存 limit、节点和容器身份。`OOMKilled` 是容器 OOM 的关键证据；退出码 137 对应 SIGKILL，再结合内核日志确定终止原因。Kubernetes 内存 limit 通过内核机制实施，达到限制时可能发生 OOM kill。[Kubernetes 官方说明](https://kubernetes.io/docs/tasks/configure-pod-container/assign-memory-resource/)

在故障节点查内核日志：

```bash
journalctl -k \
  --since '<故障日期> 01:40:00' \
  --until '<故障日期> 02:30:00'
```

提取 OOM 上下文中的 PID、进程名、cgroup、匿名内存，以及容器局部 OOM 或节点全局 OOM的信息。再查应用日志中的运行时内存异常，例如 Java 的 `OutOfMemoryError` 或 Node.js 的 heap limit 错误。

这里要分别记下**被杀进程**和**实际增长内存的进程**。如果节点上的备份或另一个 worker 消耗了内存，服务可能成为 OOM 选择的终止对象。

**2. 把三次失败与成功运行放到同一张时间线上。**

每次取任务开始前 20 分钟至结束后 20 分钟，统一时区，按“距任务开始多少秒”对齐。整理：

| 数据 | 用途 |
|---|---|
| 任务 ID、开始/结束时间、实例、重试次数 | 找重复触发和重叠执行 |
| 查询时间范围、返回行数、字段宽度、分组数 | 找数据量和聚合基数变化 |
| 读取、聚合、导出、上传各阶段进度 | 定位增长发生的阶段 |
| 每个进程、容器和节点的内存 | 定位内存归属 |
| 队列深度、并发数、数据库/上传耗时 | 找生产与消费失衡 |
| CPU、GC、CPU throttling、在线请求延迟 | 找回收或处理速度下降 |
| 版本、配置、limit 变更 | 找最近引入的触发条件 |

**“一周为什么只失败三次”是关键线索。** 优先比较这三次是否数据更多、分组更多、上传更慢、存在重试，或者与备份、日志压缩、缓存刷新等任务重叠。

**3. 按下面的优先级检查原因。**

| 优先级 | 可能原因 | 重点证据与代码位置 |
|---|---|---|
| 高 | 全量结果集持续累积 | 驱动预取、`fetchAll`、ORM 实体缓存、列表追加；内存随读取行数增长 |
| 高 | 导出对象或缓冲持续累积 | Excel 工作簿、完整 CSV/JSON 字符串、压缩包、上传缓存；内存随输出大小增长 |
| 高 | 分组、去重、排序状态增长 | 大 map/set、全量排序；内存随不同 key 数或记录数增长 |
| 高 | 无界队列、异步任务积压 | 读取快于转换/上传；队列长度、未完成 future/promise 和内存同步增长 |
| 中高 | 任务重叠或重复调度 | 每个服务副本都启动定时任务、上次任务未结束、超时重试又启动一份 |
| 中 | 对象长期持有或资源泄漏 | 全局缓存、闭包、监听器、线程本地变量、未释放 native buffer；连续运行后存活对象累积 |
| 中 | CPU/GC 或下游瓶颈 | CPU 限流、GC 时间增加、上传变慢，使在途对象和积压增加 |
| 中 | 堆外、临时文件或节点竞争 | 堆稳定而 RSS/容器用量上涨；直接内存、线程、子进程、tmpfs，或同机其他任务增长 |

特别检查报表 SQL 是否因日期边界、分页条件或 join 膨胀突然扩大结果集。数据量增加可能同时放大全量读取、聚合和导出三个阶段的内存。

**4. 把内存拆开，决定用哪种 profiler。**

cgroup v2 环境采集目标 cgroup 的 `memory.current`、`memory.max`、`memory.events` 和 `memory.stat`，同时检查父级限制。重点观察：

- `anon` 增长：优先查堆对象、native 分配、线程栈。
- `file` / `shmem` 增长：查文件缓存、tmpfs、共享内存。
- `sock` 增长：查网络缓冲和下游消费。
- `oom_kill` 计数变化：与内核日志的终止时间关联。

这些字段的具体含义见 [Linux cgroup v2 文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)。使用内存型 `emptyDir` 的报表临时文件也会消耗容器内存，重点查看文件增长曲线。[Kubernetes 资源管理说明](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)

再对比运行时指标：

- **堆内存与 RSS 一起涨**：看增长最快的对象类型、存活大小和引用链，定位持有者。
- **GC 后存活堆持续涨**：重点查结果集、聚合容器、队列和缓存。
- **堆稳定而 RSS 涨**：转向 native 分配、直接缓冲、线程、子进程和 allocator 保留内存。
- **目标进程稳定而容器涨**：查其他进程和文件内存。

在任务开始、增长中段、任务结束后各取一次 profile，比较增量。完整 heap dump 放在有足够内存和磁盘余量的复现环境采集；线上优先用低开销采样，保证能持续拿到曲线。

**5. 用受控重跑定位具体机制。**

保持版本、配置、数据快照和运行时限额一致，每次只改变一个条件：

| 实验 | 重点判读 |
|---|---|
| 报表输入量设为原来的 1/4、1/2、全量 | 峰值随数据量增长，定位全量状态；不同分组基数用于区分聚合状态 |
| 并发从当前值降到 1 | 比较峰值、增长斜率和队列深度，识别并发放大 |
| 分别执行读取、聚合、导出、上传阶段 | 找首次出现持续增长的阶段 |
| 固定输入量，改变上传或消费速度 | 看积压与内存是否同步变化 |
| 同一进程连续运行多次 | 比较每次开始前的存活对象与内存基线，定位长期持有 |
| 将任务移到其他时间或独立 worker | 区分任务自身消耗与凌晨节点竞争 |

暂停或移动一次调度后，继续观察原来凌晨 2 点的节点与服务曲线；原时段仍出现增长，就追踪同一时间运行的其他任务。

当前曲线的净增长速率约为：

```text
r = 0.4 × 内存上限 / 600 秒
```

如果上限为 8 GiB，约为 **5.5 MiB/s**。把它与每秒处理行数、输出字节数和队列增长量对应起来，就能估算每行或每个积压任务持有多少内存，并与 profile 中的对象大小核对。

**6. 根据定位结果修复，并设定验收条件。**

- 全量读取/导出：改成端到端流式处理、分页读取、分块写出，检查驱动和导出库内部缓冲。
- 聚合状态过大：数据库侧聚合、分区处理、外部排序，给单次处理范围设置预算。
- 队列积压：有界队列、背压、有界并发，限制重试数量。
- 重复调度：跨实例互斥、幂等键、租约续期、明确重试所有权。
- 长期持有：按引用链释放对象，给缓存设容量，补齐资源关闭逻辑。
- 堆外或临时文件：限制直接缓冲和线程数量，将大临时文件写到有容量预算的磁盘。
- 在线与报表竞争：独立 worker，分别配置资源和调度策略。

验收使用**已失败的数据范围及更大的输入量**：任务完整产出且结果正确；内存峰值保持在预算内；队列有界；连续多轮运行的存活对象保持稳定；在线延迟保持目标范围。告警同时覆盖使用量、增长速率和预计触顶时间，按采样与处置所需时间提前触发。
