**最可能的是报表任务在处理过程中持续保留结果集、聚合对象或导出缓冲，把线上服务剩余的内存预算耗尽。** 第二优先级是任务重复执行、并行分片或下游变慢造成积压。排查应先确认谁触发了 OOM，再定位增长发生在哪个阶段、由哪些对象或内存区域承载。

三次故障都集中在任务运行时段，且内存连续增长约 10 分钟，符合“随着处理进度持续积累”的形态。我会先检查报表的数据获取、聚合、导出、上传四段。

**1. 按优先级检查这些原因**

| 优先级 | 可能原因 | 重点检查 | 支持该判断的现象 |
|---|---|---|---|
| 最高 | 全量读取并保留数据 | `fetchAll`、ORM 实体列表、DataFrame、分页后仍追加到总列表、驱动预取 | 内存与累计读取行数同步上涨；结束后活跃对象明显减少 |
| 最高 | 导出过程保留整份报表 | Excel 工作簿、PDF 渲染、整份 CSV/JSON 字符串、压缩和上传缓冲 | 查询结束后仍增长；对象集中在单元格、字符串、字节数组 |
| 高 | 查询数据量或聚合基数异常 | 时间范围扩大、漏租户条件、分页重复、JOIN 放大、去重集合、分组键数量 | 故障日的行数、单行大小或分组数显著高于成功日 |
| 高 | 重复执行或并发叠加 | 每个服务副本都跑定时器、重试、手工补跑、旧任务未结束、并行分片 | 相同业务日期出现多个执行实例；内存随活跃任务数变化 |
| 高 | 无界队列及下游积压 | 查询速度超过生成/上传速度，异步请求一次性提交，失败批次留在重试队列 | 队列长度、未完成请求数和内存同时增长 |
| 中 | 对象被长期引用 | 全局缓存、任务历史、闭包、监听器、线程局部变量、未结束事务中的 ORM 上下文 | 任务完成并经历 GC 后，活跃对象基线仍逐轮上涨 |
| 中 | 原生内存、子进程或临时文件增长 | 压缩/渲染库、DirectBuffer、线程栈、子进程、`tmpfs` 临时文件 | 容器用量上涨，主进程托管堆比较稳定 |
| 中 | 原有内存预算偏紧或回收受阻 | 服务基线上涨、limit 下调、堆配置过大、CPU 限流、同机任务竞争 | 相同报表在更高起始内存、更低 CPU 或更慢下游条件下失败 |

其中一个常见组合是：**数据库分页读取 → 全部装进内存 → 构建完整工作簿 → 序列化成字节数组 → 上传**。多个阶段的对象同时存活，峰值会达到最终文件大小的数倍。

**2. 先把三次 OOM 的触发层确认清楚**

同时取应用日志、容器退出状态和节点内核日志，按同一时区对齐：

- **运行时 OOM**：寻找 `Java heap space`、`Direct buffer memory`、`JavaScript heap out of memory`、`MemoryError` 等完整错误及调用栈。
- **容器限制触发**：对齐 `OOMKilled`、实际 memory limit、对应 cgroup 的 `max/oom` 事件变化，以及内核中的 memcg OOM 记录。
- **节点整体 OOM**：检查内核日志中的触发进程、被杀进程、内存统计，以及凌晨其他进程的增长。
- **平台驱逐或探针重启**：检查 `Evicted`、`MemoryPressure`、探针失败和发布事件，分别记录重启链路。

Kubernetes 的 memory limit 通过内核 OOM 机制执行。退出码 137 表示进程收到 SIGKILL；结合 `OOMKilled` 和内核记录定位终止原因。[Kubernetes 资源管理文档](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)

如果线上是 Linux/Kubernetes，可以先执行这些只读检查：

```bash
kubectl get pod <pod> -n <namespace> -o yaml
kubectl describe pod <pod> -n <namespace>
kubectl logs <pod> -n <namespace> -c <container> --previous --timestamps
kubectl get events -n <namespace> --sort-by=.metadata.creationTimestamp

journalctl -k --since "<故障日期> 01:45:00" --until "<故障日期> 02:30:00"
```

重点保存容器名、Pod UID、节点、`lastState.terminated`、重启时间及当时的配置。Pod 已重建时，从集中日志和历史监控按旧 UID 查找。

还要查清“60% → 100%”的计算公式：分子是 RSS、working set、容器总用量还是堆使用量；分母是容器 limit、request、节点容量还是堆上限。后续全部同时记录**绝对字节数**。

**3. 用一张时间线把任务进度和内存增长对上**

把过去七晚的任务执行整理成表，包括成功、失败和未执行的情况：

```text
日期、版本、配置、实例、执行 ID、起始内存、
查询行数、累计读取字节、分组数、输出大小、
活跃任务数、队列峰值、各阶段耗时、内存峰值、执行结果
```

重点回答：

- 三次失败是否处理更多数据、更宽日期范围、更大单行或更多分组？
- 成功日是否起始内存更低？
- 是否只有某个副本或节点失败？
- 是否有数据库、对象存储、磁盘或网络变慢？
- 每次 OOM 是发生在固定阶段、固定处理行数，还是固定运行时长？
- 最近是否调整过查询、导出库、并发、容器 limit 或 CPU 配额？

下一次受控执行时，每 5–10 秒采集一次内存，并记录任务阶段、累计行数、输出字节、队列长度、并发数、GC 和 CPU throttling。

若分母确实是固定内存限制 `L`，当前平均净增长约为：

```text
增长速度 = 0.4 × L / 600 秒
```

例如 `L = 4 GiB`，约为 **2.73 MiB/s**。再除以处理行数/秒，可以估算每行留下多少内存；这个值适合与对象大小、队列元素大小核对。

**4. 拆分内存，再选择诊断工具**

Linux 上先看目标进程的：

```bash
cat /proc/<pid>/status
cat /proc/<pid>/smaps_rollup
cat /proc/<pid>/cgroup
```

读取对应 cgroup v2 的 `memory.current`、`memory.max`、`memory.events` 和 `memory.stat`；在宿主机上检查时，根据进程所属路径及挂载点定位，同时检查祖先 cgroup 的限制。

判断分支如下：

- **托管堆及 GC 后活跃对象增长**：追踪结果集、工作簿、聚合表、队列及持有引用。
- **进程 RSS 增长，托管堆稳定**：检查原生分配、线程栈、映射和分配器保留内存。
- **容器用量增长，主进程 RSS 稳定**：检查其他进程、文件缓存、共享内存和临时文件。
- **`file/shmem` 增长明显**：检查临时目录挂载类型、内存型 `emptyDir`、文件写入及回写压力。

`memory.stat` 的部分字段存在包含关系，按字段含义分析；`oom_kill` 记录该 cgroup 成员被各类 OOM killer 杀死的次数，结合 `max/oom` 增量和内核日志区分触发层。[Linux cgroup v2 文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

按技术栈选工具：

| 技术栈 | 建议采集 |
|---|---|
| Java | GC 日志、JFR、对象直方图；堆转储分析 retained size 和 GC roots；NMT baseline/diff 检查 JVM 原生分配，JNI 库分配另用原生工具追踪。[Oracle 文档](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshooting-memory-leaks.html) |
| Go | 对比任务前后的 heap profile，先看 `inuse_space` 的存活对象，再看 `alloc_space` 的分配热点；同时检查 goroutine 数。[Go 文档](https://go.dev/wiki/Performance) |
| Node.js | 同时记录 `rss`、`heapUsed`、`external`、`arrayBuffers`，再分析对象引用链及 Buffer 持有者。[Node.js 文档](https://nodejs.org/api/process.html) |
| Python | 提前启用 `tracemalloc`，比较阶段间快照的分配位置；NumPy、渲染等扩展库同时检查原生内存。[Python 文档](https://docs.python.org/3/library/tracemalloc.html) |

最好获取任务前、增长中、任务结束并经历 GC 后的三组数据。完整堆快照放在有额外内存和磁盘预算的隔离实例采集；Node.js 构建快照时可能把堆占用翻倍。[Node.js 快照说明](https://nodejs.org/en/learn/diagnostics/memory/using-heap-snapshot)

**5. 做几组能明确区分机制的复现**

使用故障日的同一份数据、相同版本和资源配置，每次改变一个条件：

| 实验 | 如何解读结果 |
|---|---|
| 数据量按 25%、50%、100% 增加 | 峰值随总行数上涨，优先检查全量保留；随分组数上涨，优先检查聚合结构 |
| 固定数据量，降低并发 | 峰值随并发下降，检查每个执行实例的缓冲及重复任务 |
| 固定数据量，缩小分页/批次 | 峰值随批次下降，检查批内对象；增长斜率持续，检查跨批保留 |
| 分别运行查询、生成、上传阶段 | 找到从哪个阶段开始增长，以及阶段切换时旧对象是否仍存活 |
| 有控制地减慢上传或消费端 | 队列和内存同步增长，落实背压及队列上限 |
| 同一进程连续完成多次任务 | GC 后活跃对象基线逐次上升，沿引用链查长期持有；基线稳定且峰值重复，按任务容量优化 |
| 同环境错开报表执行时间 | 增长随任务移动，继续沿报表链路查；仍固定在 2 点出现，查同时间的其他任务及节点压力 |

提高内存后的实验要记录**完成时间、峰值和任务结束后的对象基线**。固定规模任务能完成且峰值稳定时，可以据此计算容量；运行时间延长后继续增长时，应优先解决持续积累。

**6. 止血和修复顺序**

1. **先保护线上请求。** 将报表移到独立进程或 Job，设置独立资源预算。迁移前暂停自动触发或限制数据范围，保留补跑记录。
2. **限制活跃任务数。** 为同一业务日期设置互斥、幂等和有上限的重试。Kubernetes CronJob 可以配置 `concurrencyPolicy: Forbid`；多个 CronJob、应用内定时器及手工执行之间，再用业务级锁协调。[CronJob 文档](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/)
3. **让内存随批次和并发受控。** 使用数据库游标或稳定键分页，批次处理后释放引用；流式生成文件、分块上传；给每一级队列设置容量并落实背压。精确高基数聚合可下推数据库或采用磁盘溢写。
4. **配置任务级退出条件。** 超过内存预算、队列容量或执行期限时，停止读取新数据，取消子任务，释放资源并保存进度。重试沿检查点恢复。
5. **按实测峰值调整容量。** 将服务基线、任务增量、原生内存及运行波动纳入预算；Java/Node 等运行时的堆上限与容器总限制分别配置。

修复验收至少覆盖：**故障日数据、预计最大数据量、慢下游、重复触发，以及同进程连续多次执行**。验收看峰值是否受预算约束、队列是否有界、活跃对象基线是否稳定，以及线上请求延迟是否达标。

我会最先查两处：**分页结果是否被跨批追加保存，以及导出库是否在内存中保留完整工作簿和输出缓冲**；随后核对同一报表是否存在多个执行实例。这三项与当前的时间和增长形态最吻合。
