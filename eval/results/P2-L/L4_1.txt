**大概率是凌晨报表任务触发了内存超限，首查“处理过程中持续保留数据”和“任务并发或缓冲积压”。** 三次都集中在任务执行窗口，加上 10 分钟内持续上涨，已经足够把排查重点放到报表链路。决定具体修复方案的缺口是：增长发生在哪类内存、哪个阶段、哪个执行实例。

下面按“先保护线上、再定位机制、最后验证修复”的顺序展开。命令按 Linux／Kubernetes 举例。

**1. 先保护下一次凌晨执行，同时保留现场**

下一次任务前优先做这些：

- 将报表实际执行并发降到 1，覆盖多副本重复调度、任务内部并行和超时重试。
- 给读取、转换、写出之间的队列设置容量上限；写出变慢时，让读取暂停。
- 报表与接口共进程时，优先迁到独立 worker，配置独立内存预算；节点存在压力时，同时安排足够的节点容量。
- 在任务开始前启动低开销采样，将内存、任务进度和实例标识持续写到外部存储。
- 必须临时扩内存时，先核对节点余量，再同步检查运行时堆上限。

Kubernetes CronJob 可以用 `concurrencyPolicy: Forbid` 控制同一个 CronJob 创建的任务重叠；跨 CronJob、应用内调度和手工补跑需要统一的任务互斥机制。[CronJob 官方文档](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/)

**2. 确定究竟触碰了哪个内存上限**

先核实监控中“60%→100%”的分子、分母：进程 RSS、容器总内存、working set、运行时堆，还是节点内存；分母是容器 limit、堆上限，还是节点容量。拿到对应的字节值和单实例曲线。

然后区分三条路径：

| 路径 | 要找的证据 | 排查重点 |
|---|---|---|
| 容器／cgroup OOM | `OOMKilled`、内核日志中的 cgroup 路径、对应上限、OOM 计数变化 | 容器内全部进程和计费内存 |
| 运行时 OOM | 应用中的内存异常、GC 日志、崩溃报告 | 堆上限、存活对象、特定分配失败 |
| 节点 OOM／内存压力驱逐 | 节点内核日志、`MemAvailable`、Pod 的驱逐原因 | 同节点任务、系统进程和调度容量 |

Kubernetes 下先取：

```bash
kubectl describe pod <pod> -n <namespace>
kubectl get pod <pod> -n <namespace> -o yaml
kubectl logs <pod> -n <namespace> -c <container> --previous --timestamps
```

核对 `lastState.terminated.reason`、`exitCode`、结束时间、容器名称和资源配置。退出码 `137` 对应 SIGKILL，结合 `OOMKilled` 和内核记录确认来源。[Kubernetes 内存故障示例](https://kubernetes.io/docs/tasks/configure-pod-container/assign-memory-resource/)

节点上取故障窗口的内核日志：

```bash
journalctl -k --since "<故障日期> 01:40:00" --until "<故障日期> 02:30:00"
```

关注被杀 PID、进程名、cgroup 路径及 OOM 上下文。被杀进程的选择受 OOM 评分影响，继续检查该内存域里各进程的占用。

**3. 按以下优先级排查原因**

| 优先级 | 可能原因与机制 | 最有区分度的证据 |
|---|---|---|
| 最高 | **报表累计保留数据**：全量查询结果、不断追加的列表／字典、ORM 实体跟踪、全局排序或高基数分组、Excel 单元格对象 | 已处理行数增加时，存活对象和占用同步增加；对象引用链指向报表上下文 |
| 高 | **读取快于处理／写出**：数据库持续返回数据，生成文件或上传较慢，队列和 buffer 越积越多 | 队列深度、待写字节数与内存同步增长；下游耗时增加 |
| 高 | **重复执行或并行过高**：每个服务副本都调度、重试与原任务重叠、同时处理多个租户 | 同一业务日期存在多个执行实例；并发数变化与内存斜率对应 |
| 高 | **报表峰值超过剩余预算**：任务开始时已有 60% 占用，某些日期数据量更大 | 失败日期的数据量、启动基线或分组数更高；成功日期峰值接近上限 |
| 中 | **跨次执行残留**：缓存、监听器、闭包、未完成任务继续持有报表数据 | 同一进程多次完成报表后，回收后的存活对象基线逐次升高 |
| 中 | **堆外／原生内存增长**：压缩、图像、数据库驱动、直接缓冲区、线程栈、分配器保留或碎片 | 运行时存活堆较稳，RSS／匿名内存继续增长 |
| 中 | **临时文件占用内存**：报表写到 tmpfs、`/dev/shm` 或内存型 `emptyDir` | `file`／`shmem` 与临时文件大小同步增长 |
| 中 | **同时间资源竞争**：备份、ETL 或其他批任务使数据库、磁盘、CPU 变慢，报表和接口请求积压 | 先出现下游延迟／CPU 节流，随后队列及内存上涨 |

内存型 `emptyDir` 使用 tmpfs，其使用量进入内存计费；导出文件路径值得直接检查。[Kubernetes 资源管理文档](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)

**4. 用失败与成功执行的差异，解释“一周为什么只有 3 次”**

如果报表每天执行，把三次失败与其余成功执行放进同一张表：

- 代码版本、配置、内存上限、实例运行时长、启动前内存。
- 查询时间范围、实际行数、平均行宽、大字段大小、分组／去重键数量。
- 同时执行的任务数、内部并发数、重试次数。
- 查询、转换、生成文件、压缩、上传各阶段耗时。
- 输出文件大小、队列最大深度、节点位置及同节点其他任务。

**优先找失败日期共同跨过的阈值。** 例如失败都出现在更高启动基线、某个大租户、更多分组键或上传变慢时。

将每次曲线按“任务开始”对齐，再标记阶段切换。增长若总从查询开始，查结果保留；若从写出开始，查导出缓冲；若延迟之后才上涨，查积压。

假设分母是固定内存上限 \(L\)，当前观察到的平均净增长为：

\[
r \approx \frac{0.4L}{600秒}
\]

例如 \(L=8\,GiB\)，约为 **5.5 MiB/s**。再计算同一窗口的：

\[
每处理一行的净增长 \approx \frac{\Delta 内存字节数}{\Delta 已处理行数}
\]

这个数能帮助判断占用是否随着行数持续累积，并估算当前批大小和并发的预算。

**5. 下一次采样要能直接分出“堆、原生内存、文件、其他进程”**

在任务窗口每 5～10 秒采集：

- 进程 RSS、容器总内存、运行时堆使用量、回收后的存活量。
- GC 时间与次数、CPU 使用及节流、线程数。
- 读取行数、处理行数、写出行数、队列长度、待写字节数。
- 任务 ID、业务日期、实例 ID、阶段、重试编号。
- 节点可用内存、临时文件大小。

cgroup v2 环境下，在目标进程对应的 cgroup 目录读取：

```bash
cat <cgroup目录>/memory.current
cat <cgroup目录>/memory.max
cat <cgroup目录>/memory.events
cat <cgroup目录>/memory.stat
cat /proc/<pid>/smaps_rollup
```

用 `memory.stat` 的 `anon`、`file`、`shmem`、`kernel` 等字段定位增长来源；`shmem` 是 `file` 中的相关分类，分析时按字段层级处理。`memory.events` 的 `oom_kill` 记录该组进程被 OOM killer 杀死的次数，来源继续结合内核日志判断。[Linux cgroup v2 文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

根据结果继续：

- **存活堆持续上涨**：比较任务前与增长中的堆快照，按 retained size 找主要持有者，再沿引用链找到列表、缓存、工作簿或任务上下文。
- **堆稳定、RSS 上涨**：查看原生分配、直接缓冲区、线程栈、映射和分配器统计。
- **容器上涨、主进程稳定**：检查其他进程、子进程、临时文件和文件缓存。
- **完成后存活堆恢复、RSS 保持高位并趋于稳定**：继续观察分配器保留及内存复用。
- **重复执行后存活堆基线不断升高**：定位跨次持有对象和清理路径。

分配热点告诉你“哪里创建了对象”，引用链告诉你“谁一直持有对象”；两者结合才能落实到代码。

快照先在隔离环境采集，评估停顿和额外内存，再选线上采集点。内核 SIGKILL 后的现场主要依赖预先采样，因此采集要安排在增长早期。

**6. 在隔离环境做有区分度的复现**

使用故障日期的数据范围、相同代码和资源限制，并保留接近线上启动基线的负载。依次改变一个变量：

1. **单次、单并发执行**：确定单个报表的内存曲线。
2. **数据量按 25%、50%、100% 增加**：观察峰值随行数、分组数或大字段增长的关系。
3. **批大小降低**：峰值随批大小降低，支持批内峰值机制；全程仍持续累积，继续查跨批保留。
4. **分别观察查询、转换、写出、压缩、上传**：找出增长阶段。
5. **模拟慢写出／慢上传**：验证队列容量和背压。
6. **同一进程连续执行多次**：检查完成后的存活对象基线。
7. **提前或单独运行报表**：检查内存上涨是否跟随任务时间移动。

常见修复落点包括：游标或分批读取、释放 ORM 跟踪对象、流式写出、限制并行和队列、将全局排序／聚合下推或落盘、清理跨次缓存，以及给原生内存留出预算。

**7. 用最大数据量、慢下游和重复执行验收**

修复验收至少覆盖：

- 故障日期和预期最大数据量都能完成，报表结果正确。
- 慢下游时队列达到上限后读取暂停，内存进入平台区间。
- 同一进程多次执行后，存活对象基线稳定。
- 在正常接口负载下，报表峰值仍有明确余量，接口延迟满足目标。
- 重试、补跑和多副本场景遵守互斥与幂等规则。

容量按“服务高位基线＋报表增量峰值×实际并发＋预留余量”核算。告警同时看占用与增长速度：

\[
预计触限时间 \approx \frac{上限-当前占用}{近期净增长速度}
\]

结合剩余任务量判断是否能安全完成，提前暂停读取或取消任务。**现在最该做的是拿到三次 OOM 的来源记录，以及失败／成功报表的行数、并发、阶段耗时和内存分项；这几项通常能把问题迅速收敛到具体机制。**
