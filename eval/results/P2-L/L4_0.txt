**大概率是报表任务触发了持续的内存积累，最终撞到内存上限；优先排查全量数据或输出缓冲、处理队列积压，以及任务并发叠加。** 三次都集中在同一时间窗口，且重启前持续增长，排查重点应放在报表执行路径。决定性的证据是：**哪个进程、哪类内存，从报表的哪个阶段开始增长。**

下面按线上排查顺序展开；命令以 Linux / Kubernetes 为例。

**1．先确认 OOM 的来源和内存监控口径**

把三次事故各自的以下信息保留下来：重启时间、容器和进程身份、所在节点、退出原因、当时的内存上限、应用最后日志、内核 OOM 日志。

需要分清三条路径：

| 路径 | 关键证据 | 排查方向 |
|---|---|---|
| 容器或上级 cgroup 达到内存限制 | 内核记录 memory cgroup OOM，相关限制附近发生 kill | 该资源组中的应用、子进程和内存组成 |
| 节点整体内存耗尽 | 内核记录全局 OOM，节点 `MemAvailable` 耗尽 | 同节点所有进程和凌晨任务 |
| 运行时自身内存耗尽 | 应用记录 heap、direct memory 等分配失败 | 堆限制、存活对象、原生内存及运行时配置 |

Kubernetes 中先取：

```bash
kubectl describe pod <pod> -n <namespace>
kubectl get pod <pod> -n <namespace> -o yaml
kubectl logs <pod> -n <namespace> -c <container> --previous --timestamps
```

重点看 `lastState.terminated`、`OOMKilled`、退出时间、资源配置和探针事件。退出码 `137` 表示收到 `SIGKILL`；用终止原因和内核记录确认触发来源。Pod 被替换后，历史信息应从集中日志和监控中获取。

在对应节点取事故窗口的内核日志：

```bash
journalctl -k --since "<开始时间>" --until "<结束时间>"
```

搜索 `oom`、`Killed process`、`Memory cgroup`、`Out of memory`，核对被杀 PID、进程名和 cgroup。**节点全局 OOM 时，消耗内存的任务与被杀的服务可能分属不同进程。**

同时确认“60% → 100%”的分子和分母：

- 分子：进程 RSS、容器总使用量、working set，还是运行时堆占用？
- 分母：容器 limit、节点物理内存，还是堆上限？
- 展示：原始采样点，还是监控界面的插值、平均值或多副本聚合？

Kubernetes 的 memory limit 与 request 分别参与内存限制和调度判断，排查时核对实际生效配置。[Kubernetes 官方资源说明](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)

**2．按优先级检查这些原因**

| 优先级 | 可能原因 | 与当前现象吻合的机制 | 最有价值的验证 |
|---|---|---|---|
| 高 | 查询结果、转换结果持续保存在内存 | 每处理一批，列表、Map、ORM 会话或 DataFrame 增大 | 内存增量与累计处理行数同步；对象引用落在报表上下文 |
| 高 | 报表输出持续缓冲 | Excel 工作簿、字符串、序列化结果、压缩或上传缓冲逐步增大 | 拉取阶段平稳，生成或上传阶段开始增长 |
| 高 | 生产快于消费，队列积压 | 查询不断产出，下游写文件、上传或发送变慢 | 待处理条数、字节数、未完成异步任务数同步增长 |
| 中高 | 并发任务或重复调度 | 多副本各执行一遍、租约到期、超时重试、上次任务未结束 | 同一逻辑报表出现多个活跃执行记录，内存斜率随并发数变化 |
| 中 | 聚合维度基数或数据量超预期 | 去重集合、分组 Map、关联查询结果随数据持续扩大 | 失败日的唯一键数、实际查询行数或最大记录尺寸明显升高 |
| 中 | 任务保留对象，形成长期泄漏 | 缓存、监听器、线程本地变量、全局集合持续持有结果 | 成功执行并完成正常回收后，存活对象和内存基线逐次抬升 |
| 中 | 原生内存、分配器或子进程增长 | 堆外缓冲、压缩库、线程、原生库或报表渲染进程消耗内存 | 运行时存活堆平稳，RSS 或其他进程持续增长 |
| 中 | 文件缓存、tmpfs 或共享内存增长 | 临时文件和内存文件系统占用计入资源组 | cgroup 的 `file`、`shmem` 随生成文件增长 |
| 中 | 基线偏高、资源预算不足 | 正常报表峰值超过剩余空间 | 相同输入、单次执行有稳定峰值，但峰值超过当前预算 |

我的排序依据是：**近似线性增长更符合“稳定吞吐下，每单位工作持续留下一部分内存”的机制。** 泄漏、全量累积和队列积压都可能形成这种曲线，下一步通过业务进度与内存组成区分。

另外，检查凌晨同时间运行的备份、日志压缩、索引构建和缓存预热；它们可能争夺节点内存，也可能拖慢报表下游，间接造成积压。

**3．用失败日与成功日，把条件找出来**

如果报表每天执行，另外四天的成功运行是最有价值的对照。统一时区，以实际任务开始时间对齐，比较：

| 比较项 | 要找的差异 |
|---|---|
| 任务开始前内存及进程运行时长 | 失败是否由更高基线或多日累积触发 |
| 实际输入行数、查询时间范围、唯一键数量 | 是否存在周报、补数据或日期边界导致的数据放大 |
| 活跃任务数、重试数、租约状态 | 是否存在重复执行和重叠 |
| 各阶段耗时、处理与输出速度 | 是否存在下游变慢、队列积压 |
| 部署版本、配置、limit 和堆上限 | 是否由代码或资源配置变更触发 |
| 节点其他任务和内存余量 | 是否集中在特定节点或共用任务窗口 |

为每次运行建立一条时间线：

```text
任务开始 → 查询 → 转换/聚合 → 生成文件 → 上传 → 清理
```

在上面叠加内存、累计处理行数、队列字节数和并发数。重点定位**内存增长的起点与斜率变化对应哪个阶段**。你给出的“重启前十分钟”也要向前扩展到整个任务和任务前基线。

若百分比以固定限制 `L` 为分母，则这十分钟的平均净增长为：

```text
g = 0.4 × L / 600 秒
```

例如 `L = 8 GiB`，净增长约为 `5.46 MiB/s`。再除以每秒处理行数，可以估算每行留下的内存量，与记录对象、输出缓冲或队列元素的实际大小核对。

**4．下一次执行时，采集能直接分流的证据**

从任务开始前持续采集到任务结束及回收阶段，建议先用 5～10 秒间隔，按进程、容器和任务执行 ID 分别记录。

采集四组数据：

- **进程**：RSS/PSS、匿名内存、文件映射、共享内存、线程数、子进程。
- **cgroup**：当前用量、限制、OOM 计数、匿名内存、文件与共享内存、内核内存。
- **运行时**：已用堆、正常 GC 后的存活堆、分配速率、GC 耗时、堆外内存。
- **业务**：阶段、累计行数、累计输出字节数、队列条数和字节数、活跃任务与重试数。

Linux 进程可读取：

```bash
cat /proc/<pid>/status
cat /proc/<pid>/smaps_rollup
cat /proc/<pid>/cgroup
```

`smaps_rollup` 汇总进程映射的内存统计，可用来追踪 RSS/PSS 及匿名、文件和共享内存的变化。[Linux `/proc` 文档](https://docs.kernel.org/filesystems/proc.html)

cgroup v2 在目标资源组目录读取：

```bash
cat <cgroup-dir>/memory.current
cat <cgroup-dir>/memory.max
cat <cgroup-dir>/memory.events
cat <cgroup-dir>/memory.stat
```

同时检查上级 cgroup 的限制和事件。比较 `oom`、`oom_kill` 的增量，并用内核日志定位触发范围；重建后的资源组要单独标识。`memory.stat` 中部分字段存在包含关系，例如 `shmem` 包含在 `file` 中，按字段含义分析。[Linux cgroup v2 文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

采集后的分流判断如下：

| 观察结果 | 下一步 |
|---|---|
| GC 后存活堆持续上涨 | 比较对象数量、保留大小和引用链，找报表集合、全局缓存、队列及任务上下文 |
| 已用堆呈锯齿，GC 后基线稳定，RSS 上涨 | 检查堆提交量、原生分配、分配器保留、线程和映射 |
| 队列字节数与内存同步上涨 | 定位最慢消费者，检查背压和在途任务上限 |
| 服务 RSS 平稳，cgroup 用量上涨 | 检查子进程、文件缓存、tmpfs、共享内存及内核内存 |
| 内存斜率随活跃任务数增加 | 追查重复调度、锁租约、重试和并发设置 |

对象分析优先在隔离复现环境做；线上先采轻量指标和分配采样。完整快照安排在有内存、磁盘和暂停预算的时候，提前采集。

**5．先控制下一次事故，再做可控复现**

优先把报表放到独立 worker 或 Job，配置独立内存预算；共用节点时也核对节点余量。随后限制执行并发、在途批次、队列字节数和自动重试，并检查服务重启后是否立即重跑同一报表。

短期处理按定位结果选择：

- 全量累积：采用经过验证的流式读取、分批转换和流式输出；每批完成后释放引用。沿数据库驱动、ORM、转换、导出、上传逐层核对缓冲行为。
- 队列积压：设置有界队列和背压，按字节控制容量；让读取速度跟随下游吞吐。
- 高基数聚合：把聚合下推到数据库，或采用分区、外部排序及磁盘溢写。
- 并发叠加：限制同一逻辑报表的活跃执行数，补齐租约续期、重复执行防护和幂等。
- 资源预算不足：在节点余量明确后临时增配，记录调整后的斜率和完成峰值。

按当前斜率，增加 `ΔM` 内存大致增加 `ΔM/g` 的执行时间。这个估算可以判断临时扩容是否足以让任务完成。

复现使用失败日输入，固定版本和资源配置，每次改变一个变量：

| 实验 | 支持的机制 |
|---|---|
| 同样数据，单任务执行，再逐步增加并发 | 峰值随并发增加，支持并发内存叠加 |
| 改变总数据量，保持批次和并发固定 | 峰值随总量增长，支持累计保留 |
| 改变批次大小，保持总量固定 | 峰值随批次变化，支持批次工作集过大 |
| 控制下游速度 | 下游变慢时队列和内存同步增长，支持积压 |
| 同进程连续执行多轮 | 每轮回收后的存活对象增加，支持长期保留 |
| 数据拉取、聚合、导出、上传逐段测量 | 找到主要增长阶段及其对象或缓冲 |

**6．用明确的验收结果结束排查**

修复验收至少覆盖失败日输入、预期最大数据规模、最大允许并发，以及同进程多轮执行。看三个结果：

- 内存峰值落在预算内，并为在线业务波动及原生内存留出空间。
- 采用流式设计的路径中，固定批次和并发后，内存能达到平台；累计数据量继续增加时保持受控。
- 每轮任务结束后，存活对象和内存基线稳定；并发、重试和下游变慢时，队列与在途数据保持有界。

**现在最值得先做的动作是：取三次事故的终止与内核记录，对齐成功日和失败日的阶段时间线，再给下一次报表补上“存活堆、cgroup 内存组成、队列字节数、活跃任务数”四组指标。** 这四组数据能最快把排查收敛到具体机制和代码路径。
