**大概率是定时报表触发了持续的内存积累，最终撞上内存上限；优先查全量数据驻留、导出缓冲和任务并发叠加。**三次都集中在凌晨 2 点，且重启前持续爬升，报表执行路径是首要嫌疑。决定性证据是：增长发生在哪个进程、哪类内存，以及它与报表处理进度的对应关系。

**1. 先按下面的顺序排查原因。**

| 优先级 | 可能原因 | 典型机制 | 最有效的验证方式 |
|---|---|---|---|
| 高 | 查询结果持续留在内存 | 全量查询、分页结果不断 `append`、ORM 会话保留实体、聚合表随数据增长 | 比较累计处理行数与存活对象大小；检查列表、映射、ORM 会话的引用 |
| 高 | 报表生成器持续缓存 | Excel 工作簿保存全部单元格；CSV、JSON、ZIP 先写内存；最终上传再复制一份 | 分阶段记录内存，查看工作簿、字符串、字节数组和输出缓冲的增长 |
| 高 | 并行任务或队列积压 | 多副本重复执行、重试重叠、一次启动大量异步任务；读取速度超过生成或上传速度 | 查所有实例的任务 ID、活跃任务数、队列长度和消费者吞吐 |
| 中 | 当天数据量或数据形态异常 | 行数增多、宽字段增大、时间范围扩大、JOIN 膨胀、分组键数量增多 | 对比失败日和成功日的行数、字节数、查询参数与聚合基数 |
| 中 | 对象跨批次、跨任务残留 | 全局缓存、闭包、回调、线程本地变量、失败任务状态持续持有结果 | 对比任务结束并完成回收后的存活对象，沿引用链找到持有者 |
| 中 | 堆外或原生内存增长 | 压缩、图片处理、数据库驱动、直接缓冲、子进程或分配器碎片 | 对比进程 RSS、运行时堆、原生内存及子进程占用 |
| 较低，但应早确认 | 节点压力或资源配置变化 | 同时跑备份、其他容器增长、内存限制调低、运行时堆预算挤占其他内存 | 查内核 OOM 记录、节点内存、实际资源限制和配置变更 |

其中，**10 分钟线性上涨最值得优先验证“每处理一批数据，就净留下固定大小的对象或缓冲”**。如果队列长度也线性增长，则优先检查生产与消费速度差。

**2. 保存三次事故记录，确认是谁触发了 OOM。**

把每次事故前后至少 30 分钟的数据保留下来：

- 精确重启时间、实例 ID、进程 PID、节点、部署版本。
- 报表开始时间、任务 ID、参数、重试次数和最后完成阶段。
- 内存原始指标及计算公式：60% 和 100% 的分母是容器限制、节点内存，还是运行时堆上限。
- 退出原因、应用日志、内核日志、实际生效的内存配置。

如果使用 Kubernetes，先查对应容器：

```bash
kubectl describe pod <pod> -n <namespace>
kubectl get pod <pod> -n <namespace> -o yaml
kubectl logs <pod> -n <namespace> -c <container> --previous --timestamps
```

重点看 `lastState.terminated`、`reason`、`exitCode`、`finishedAt` 和 `resources.limits.memory`。退出码 137 表示被 SIGKILL，结合 `OOMKilled`、内核日志和 OOM 计数确定触发原因。容器内存限制通过内核 OOM 机制执行。[Kubernetes 内存资源文档](https://kubernetes.io/docs/tasks/configure-pod-container/assign-memory-resource/)

按证据进入三个分支：

- **运行时内存耗尽**：日志出现 Java `OutOfMemoryError`、V8 heap OOM 等，继续定位堆、直接内存、线程或对应分配限制。
- **容器限额触发**：核对目标 cgroup 的限制、使用量和 OOM 事件。
- **宿主机内存耗尽**：查节点同期全部进程、容器和定时任务，定位主要内存消费者与被杀进程。

Linux cgroup v2 下，检查目标 cgroup 的 `memory.current`、`memory.max`、`memory.events`、`memory.events.local`、`memory.stat`，并关联内核日志。事件计数按采样增量观察；重启后可能对应新的 cgroup。[Linux cgroup v2 文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

**3. 对齐七天时间线，尤其比较成功的四天。**

如果报表每天执行，四次成功运行是现成的对照。建议整理成一张表，每次执行记录：

- 开始前内存、峰值内存、结束后内存。
- 输入行数、输入字节数、唯一分组键数、输出大小。
- 查询、转换、聚合、生成、压缩、上传各阶段耗时。
- 活跃任务数、批次大小、队列长度、重试次数。
- 同期在线请求量、数据库与上传端延迟。

重点寻找以下对应关系：

- **内存增量与累计行数成比例**：转向全量结果驻留、聚合状态或导出对象。
- **增长斜率随活跃任务数增加**：转向并发叠加。
- **数据库读取正常，上传变慢且队列增长**：转向缓冲积压和背压。
- **失败日开始前内存更高**：检查长期残留与在线负载占用。
- **运行时间更长的日子失败**：检查下游变慢、重试和长时间累积。
- **上涨早于报表开始**：将排查范围扩到备份、缓存刷新、日志处理等同期任务。

统一调度器、应用、监控的时区，用任务 ID 对齐事件。还要查看原始采样点，确认图表中的直线是否经过插值或聚合。

可以把现有现象换算成预算：设监控分母为固定内存上限 \(L\)，则这段时间的平均净增长为：

\[
g \approx \frac{0.4L}{600\text{ 秒}}
\]

例如 \(L=4\,GiB\)，净增长约为 **2.73 MiB/s**。再计算：

\[
\text{每行净驻留内存}
\approx
\frac{\text{同一时间段的内存增量}}{\text{处理行数增量}}
\]

这个值可以与行对象、聚合项、单元格或队列元素的大小直接核对。

**4. 下一次执行时，把增长定位到阶段和内存类型。**

从任务开始前采集，建议先用 **5～10 秒**粒度，同时记录：

```text
时间、实例、任务ID、阶段
累计读取/处理/写出行数
活跃任务数、批次大小、队列长度、缓存条目数
进程RSS、运行时堆使用量、GC后存活量
容器内存、子进程内存、阶段吞吐与耗时
```

根据增长位置决定工具：

| 观察结果 | 下一步 |
|---|---|
| 堆使用量、GC 后存活量持续增长 | 比较对象类型和引用链，找持续持有数据的容器 |
| 堆在回收后明显下降，峰值仍触顶 | 查批次大小、瞬时复制、并发分配和 GC/CPU 压力 |
| RSS 增长，堆基本稳定 | 查直接缓冲、原生库、线程、内存映射和分配器 |
| 容器内存增长，主进程 RSS 平稳 | 查子进程、其他进程、文件缓存和共享内存 |
| `memory.stat` 的 `shmem` 增长 | 查 `/dev/shm`、tmpfs 和内存型临时目录 |

`memory.stat` 中的 `anon`、`file`、`shmem` 等字段存在包含关系，分析时按字段含义拆分。[Linux 内存统计说明](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

按运行时选择取证工具：

- **Java**：GC 日志、JFR 分配采样；必要时比较对象直方图或 heap dump，查 retained size 与 GC root。原生内存使用 NMT，先确认已启用。[Oracle 诊断工具](https://docs.oracle.com/en/java/javase/17/troubleshoot/diagnostic-tools.html)
- **Go**：比较任务前后的 heap profile，重点看 `inuse_space` 的存活分配和 `alloc_space` 的累计分配。[Go 内存分析文档](https://go.dev/wiki/Performance)
- **Python**：提前启用 `tracemalloc`，对比快照的调用栈增量；原生扩展占用结合 RSS 和对应分配工具分析。[Python tracemalloc 文档](https://docs.python.org/3.14/library/tracemalloc.html)
- **Node.js**：同时记录 `rss`、`heapUsed`、`external`、`arrayBuffers`，其中 `arrayBuffers` 已包含在 `external` 中。[Node.js 内存指标](https://nodejs.org/api/process.html)

重型快照放在有足够余量的隔离实例上采集。Node.js heap snapshot 会暂停主线程，并可能需要约两倍堆空间，采集时机应提前到增长初期。[Node.js 快照说明](https://github.com/nodejs/learn/blob/main/pages/diagnostics/memory/using-heap-snapshot.md)

**5. 在隔离环境做单变量复现，按结果落修复。**

使用相同代码、失败日输入、内存限制和代表性的在线负载，依次做这些实验：

1. **只跑一个任务，关闭自动重试。**仍然增长，就沿单任务的数据处理路径定位。
2. **分别跑小、中、大三档输入。**峰值随总行数增长，检查全量驻留；随唯一键数增长，检查聚合表。
3. **减小批次，保持总输入量相同。**峰值明显下降，调整批次与缓冲预算；持续增长保持原趋势，继续查跨批次引用。
4. **分阶段替换处理链。**依次测试读取后丢弃、转换后丢弃、真实生成、真实上传，找到增长开始的阶段。
5. **主动降低写出或上传速度。**观察队列与内存，验证背压是否有效。
6. **同一进程连续执行多次，再测试异常和取消路径。**观察 GC 后存活量、队列、缓存和资源是否回到稳定区间。

代码检查优先覆盖：

- `fetchAll`、`collect`、`list`、`toArray`、分页后汇总等全量物化。
- 数据库驱动是否真正流式读取，ORM 会话是否持续跟踪实体。
- 全局排序、去重、JOIN、分组是否需要保存全部状态。
- 工作簿、输出字符串、压缩和上传是否形成多份完整副本。
- 无界队列、大量 future/promise、失败重试是否保留输入。
- 完成、异常、取消时，游标、缓冲、临时文件和任务引用的释放。

修复方向随证据确定：全量驻留改为端到端流式处理；大聚合改为分区、落盘或数据库侧处理；积压加有界队列与背压；并发叠加加全局并发预算和跨副本互斥；残留则修复引用和清理路径。

**6. 今晚先控制事故，再验证修复效果。**

建议先执行以下措施：

- 保存事故证据，将报表迁到有独立内存限额的 worker；同节点运行时同时核对节点余量。
- 暂时串行执行，限制重试，检查跨实例重复调度和重启后补跑。
- 给批次、队列和缓冲设上限，内存接近预算时停止取数、排空或保存检查点。
- 若临时增加内存，用实测增长速度和剩余工作量估算所需容量，同时核对节点容量及运行时堆外预算。

Kubernetes CronJob 的 `concurrencyPolicy: Forbid` 控制同一个 CronJob 创建的 Job；跨 CronJob 和应用内部调度仍需统一互斥机制。[CronJob 并发策略](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/)

修复验收要覆盖失败日数据、预期最大数据、慢上传、重试和重复执行。目标是：**峰值符合预算、队列有界、任务结束后的存活对象稳定、在线延迟达标、连续多次执行没有基线抬升。**

当前最有价值的下一步是：**拿三次 OOM 的终止记录，与七次报表的行数、阶段耗时、并发数对齐；随后在隔离实例记录“累计处理行数—GC 后存活量—RSS”三条曲线。**这组证据通常能迅速把问题缩到数据驻留、缓冲积压、并发叠加或堆外增长中的一个分支。
