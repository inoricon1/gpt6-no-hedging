**大概率是报表任务触发了内存耗尽，首查任务内持续保留数据、导出缓冲和任务并发；具体根因要用内存分项与任务进度对齐确认。**

三次故障都集中在同一执行窗口，而且重启前连续增长约 10 分钟，我会优先检查报表执行路径。线性曲线尤其值得查：每处理一批数据，是否都有一部分对象、缓冲或待执行任务留在内存里。

下面按优先级展开，命令以 Linux／Kubernetes 为例。

**1. 先确认谁触发了 OOM、谁被杀，以及“100%”的分母**

把三次故障的以下信息放在同一张时间线上：

- 报表开始时间、执行实例、任务 ID、重试次数、最后完成的阶段。
- 被杀的进程／容器、退出原因、内存限制、重启时间。
- 进程 RSS、容器内存、节点可用内存、运行时堆占用。
- 同期备份、ETL、日志压缩、其他定时任务和业务流量。

Kubernetes 下先取：

```bash
kubectl describe pod <pod> -n <namespace>
kubectl logs <pod> -n <namespace> -c <container> --previous --timestamps
kubectl get pod <pod> -n <namespace> -o yaml
```

重点看 `lastState.terminated`、`reason`、`exitCode`、`finishedAt` 和 `resources.limits.memory`。`OOMKilled` 是关键证据；退出码 137 表示进程被 SIGKILL 结束，需要结合终止原因与节点日志判断触发来源。[Kubernetes 内存限制文档](https://kubernetes.io/docs/tasks/configure-pod-container/assign-memory-resource/)

节点侧查故障时间窗口的内核日志：

```bash
journalctl -k --since "<故障前时间>" --until "<故障后时间>"
```

据此分三条路径：

| 证据 | 判断与排查方向 |
|---|---|
| 容器达到限制，节点仍有余量 | 报表所属容器内存预算被耗尽，重点查进程、子进程和缓冲 |
| 节点可用内存耗尽，多个服务受影响 | 查整个节点的内存消费者与凌晨任务叠加 |
| 应用日志出现运行时 OOM，例如 Java heap space | 查运行时堆限制、存活对象和分配行为 |

同时确认监控的 60%→100% 是按容器 limit、节点总内存还是运行时堆上限计算，以及图表是否做了跨实例聚合或平滑。后续分析使用**故障实例的字节数**。

**2. 原因按这个顺序查**

| 优先级 | 可能原因 | 最有效的验证方式 |
|---|---|---|
| 最高 | **查询结果或中间结果持续累积**：全量查询、分页后继续追加总列表、ORM 会话保留实体、去重集合越来越大 | 对齐累计读取行数和内存；比较对象快照中的列表、实体、字符串、Map |
| 最高 | **报表导出持续持有数据**：Excel 工作簿、共享字符串表、图片、内存文件、压缩或上传缓冲 | 分开记录读取、聚合、渲染、压缩、上传阶段；用流式输出或临时文件做对照 |
| 高 | **重复执行或并发放大**：多个副本各自调度、租户并行、前次未结束、超时后旧任务继续运行 | 按报表业务键汇总所有实例的任务开始／结束记录，统计实际同时运行数 |
| 高 | **生产快于消费**：查询线程不断投递批次，写文件或上传较慢，无界队列积压 | 同时监控入队速率、出队速率、队列长度、在途批次数 |
| 中 | **失败日期的数据量或形态异常**：补数、重复数据、大字段、过滤条件扩大、分组键基数变高 | 比较成功日与失败日的行数、总字节数、最大字段、分组数和输出大小 |
| 中 | **跨任务保留对象或基线逐日上升**：缓存无界、监听器／闭包保留引用、任务上下文未释放 | 比较每次任务结束后的存活堆和下一次任务开始前的基线 |
| 条件性 | **堆外／本地内存、子进程或 tmpfs 增长**：直接缓冲、原生库、线程、PDF 渲染进程、内存临时目录 | 堆稳定时继续拆 RSS、进程树、线程数和 cgroup 内存分项 |
| 条件性 | **节点其他任务或配置变化**：备份与报表叠加、limit 下调、堆上限挤占容器余量 | 对齐节点消费者、发布记录、资源配置与故障日期 |

**分页代码和“流式”接口要一路检查到输出端。** 数据库驱动可能预取全部结果，应用可能把分页结果合并，导出库可能保留整份文档，上传 SDK 也可能再次读入整个文件。

**3. 用成功的四天解释失败的三天**

这组对照很有价值。七天分别记录：

`任务前内存、进程启动时间、数据量、分组数、并发数、任务耗时、输出大小、代码版本、内存限制`

主要找三种模式：

- **失败日数据更多，增长速度接近**：优先判断为单次任务容量越界。
- **失败日任务更慢，队列或并发更多**：优先判断为积压、重叠或重试放大。
- **数据量接近，失败日前基线更高**：优先查跨任务保留、长期缓存增长或其他工作负载。

如果百分比的分母固定为限制 \(L\)，目前的平均增长速度约为：

\[
r \approx \frac{0.4L}{10\text{ 分钟}}=0.04L/\text{分钟}
\]

例如限制为 4 GiB，增长约 **164 MiB／分钟**。再除以每分钟处理行数，可以估算每行净保留多少字节。这能帮助判断增长更贴近原始数据、对象膨胀还是导出内容。

**4. 下一次执行前补齐观测，在增长中段抓证据**

执行窗口内建议每 10～15 秒采样，并统一带上任务 ID 和实例 ID：

- 内存：RSS、容器用量、运行时已用堆、GC 后存活堆、堆外指标。
- 任务：当前阶段、累计行数、分组数、输出字节数、活动任务数。
- 管道：队列长度、在途批次、读取／处理／写出速率。
- 系统：线程数、子进程内存、节点可用内存、磁盘与上传延迟。

cgroup v2 下取目标 cgroup 的 `memory.current`、`memory.max`、`memory.events` 和 `memory.stat`。重点拆 `anon`、`file`、`shmem`、`kernel`；`shmem` 属于 `file` 的细分项，汇总时避免重复计算。结合 OOM 事件计数和节点日志定位触发范围，并将这些指标持续存到外部监控。[Linux cgroup v2 文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

内存画像建议在**任务前、明显增长时、接近预设停止阈值时**取样：

| 技术栈 | 首选证据 |
|---|---|
| Java | GC 日志、类直方图、堆引用链；RSS 增长超出堆增长时查 Native Memory Tracking，需预先启用。[jcmd 文档](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jcmd.html) |
| Node.js | 同时记录 `rss`、`heapUsed`、`external`、`arrayBuffers`，增长阶段再取分配画像或堆快照。[内存指标文档](https://nodejs.org/api/process.html#processmemoryusage) |
| Python | 用 `tracemalloc` 快照差分找 Python 分配来源；RSS 的剩余增长再查原生库与子进程。[tracemalloc 文档](https://docs.python.org/3/library/tracemalloc.html) |

完整堆快照可能暂停进程并增加资源占用，优先在隔离实例采集。内核 SIGKILL 会直接结束进程，证据采集应在达到限制前完成。

**5. 在隔离环境做三个有判别力的实验**

使用失败日相同的数据范围、版本和内存限制，每次只改变一个因素：

1. **单任务执行，并关闭自动重试。** 观察增长是否仍出现，定位单任务开销或并发放大。
2. **数据量取 25%、50%、100%。** 比较峰值与任务结束后的存活内存。峰值随数据量增长，重点查全量持有；重复运行后基线抬升，重点查跨任务保留。
3. **分别替换输出端、缩小批次、限制队列。** 先只读与计算，再启用真实导出和上传；观察是哪一步恢复了原有增长曲线。

最有用的三个读数是：

- 每累计处理一批，内存净增加多少。
- 队列长度是否与内存一起增长。
- 任务结束、对象释放且运行时完成回收后，存活内存回到什么水平。

RSS 可能受分配器保留影响；跨次泄漏的判断重点放在存活对象与引用链上。

**6. 止血和修复分别落地**

下一次凌晨执行前，优先把报表迁到独立 worker／容器，设置独立资源预算；同时限制并发、队列和自动重试，为同一报表业务键加互斥与幂等控制。临时扩容可以争取采证时间，额度按实测峰值及节点容量确定。

根因修复对应为：

- 数据累积：游标／分批读取、每批释放 ORM 会话、限制缓存；大规模聚合或排序下推数据库或使用外部排序。
- 导出累积：流式写出、磁盘临时文件、限制上传缓冲与在途分片。
- 消费积压：有界队列、背压、受控并发。
- 跨次保留：沿引用链修复缓存、任务上下文、监听器和资源释放。
- 预算不足：给业务基线、任务峰值、堆外开销和波动分别留预算。

验收用失败日数据和预期增长后的数据，连续跑多轮：确认峰值处于预算内、队列受控、任务结束后的存活内存稳定、报表结果正确，再覆盖完整凌晨调度窗口。

**我会先做两件事：保存三次 OOM 的容器与节点证据；将七天的任务数据量、实际并发数、任务前内存和内存增长曲线对齐。** 这一步通常能迅速决定后续主攻单任务累积、并发积压，还是逐日升高的基线。
