**优先怀疑请求在等：下游 I/O、连接池或线程池排队、锁竞争。** 这些都能让 p99 翻倍，同时让 CPU 保持在 30%。先把慢请求的 800ms 拆成“执行时间”和“等待时间”，最快能定位方向。

按这个顺序查：

| 原因 | 典型表现 | 重点看什么 |
|---|---|---|
| 下游变慢：数据库、缓存、RPC | 慢请求集中在某个调用；超时重试进一步拉长尾延迟 | 慢请求 trace 的子 span、下游 p99、重试次数；数据库慢 SQL 和锁等待 |
| 连接池、线程池或并发限额耗尽 | 请求先排队，实际执行仍很快；CPU 留有余量 | 获取连接耗时、池内活跃数、等待数、任务队列长度 |
| 锁竞争或串行热点 | 多个请求卡在同一个位置；某个线程或核心很忙 | 线程栈、锁等待 profile、逐核 CPU、热点 key |
| GC、调度或容器 CPU 限流 | 延迟周期性尖峰，多个请求同时变慢 | GC pause、运行队列、容器 throttling 指标；CPU 使用率的统计窗口 |
| 磁盘或网络抖动 | 偶发长等待，平均耗时变化较小 | 磁盘延迟和队列、TCP 重传、连接建立与 DNS 耗时 |

**第一步具体做：**取上涨前后的慢请求 trace，比较每段耗时；同时对齐 QPS、在途请求数、池等待数和发布记录。特别检查埋点是否覆盖入口排队、获取连接和重试间隔——这几段经常藏着新增的 600ms。

如果 QPS 同期上涨、执行耗时基本稳定、池等待明显增加，就优先按容量排队处理：找出占满并发的环节，缩短资源占用时间，并在入口限制并发。**直接扩连接池可能把排队转移到数据库，先看下游的承载情况。**
