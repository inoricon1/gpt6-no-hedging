大概率是请求的等待时间变长了，优先查下游调用、连接池排队和锁竞争；CPU 30% 也可能掩盖单核饱和或容器限流。

| 可能原因 | 为什么 CPU 仍然低 | 最直接的验证 |
|---|---|---|
| **数据库或下游变慢** | 请求在等网络、磁盘、数据库锁或远端响应 | 看慢请求 trace，定位耗时增加最多的调用；查 SQL 耗时和锁等待 |
| **线程池、连接池耗尽** | 请求排队等 worker 或连接 | 看排队时长、队列深度、活跃连接数，以及获取连接的耗时 |
| **应用锁竞争** | 线程阻塞在锁上，参与计算的线程少 | 连续抓几次线程栈，查看重复的阻塞位置和锁持有者 |
| **单核饱和、CPU 配额限流** | 整机平均值稀释热点；容器达到配额后被暂停调度 | 看每核利用率、热点线程、容器 CPU throttling |
| **GC 或运行时暂停** | 少量长暂停明显抬高尾延迟，平均 CPU 变化小 | 将 GC pause、safepoint 时间与延迟尖峰对齐 |
| **流量突发、重试或超时** | 短时排队被监控平均值抹平；重试拉长请求时间 | 看秒级 QPS、在途请求数、重试次数，以及慢请求耗时是否集中在固定值附近 |

**第一步抓上涨后的慢请求 trace，并与正常请求比较，把 800ms 拆成“入口排队、应用执行、下游等待”。** 找到新增的约 600ms 落在哪一段，再查对应的池、锁或下游。若各段调用耗时都正常，重点补查入口排队、调度延迟和运行时暂停。
