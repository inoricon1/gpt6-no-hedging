大概率是请求在等下游、连接池或锁，也可能有单核打满或 CPU 配额限流；优先定位新增的 600ms 花在哪个阶段。

CPU 30% 很常见：请求等数据库、网络、锁时几乎不消耗 CPU；少量慢请求就足以把 p99 拉到 800ms。

按这个顺序排查：

| 原因 | 典型表现 | 看什么 |
|---|---|---|
| **下游变慢**：数据库、缓存、外部服务 | 慢请求集中在某个调用，可能伴随重试 | 慢请求 trace、慢 SQL、下游耗时与重试次数 |
| **连接池或工作线程池排队** | 流量或并发上涨，池持续满载 | 获取连接耗时、pending 数、活跃线程、队列长度 |
| **锁竞争或串行瓶颈** | 并发越高越慢，线程大量等待 | 线程栈、锁等待、off-CPU profile |
| **GC 或运行时停顿** | 延迟周期性尖峰，同进程多个请求一起变慢 | GC pause、事件循环延迟、内存分配速率 |
| **局部 CPU 瓶颈或配额限流** | 某个核、线程或实例忙，整体 CPU 仍低 | 每核/每实例 CPU、热点线程、容器 throttling |
| **网络异常** | 建连或读取变慢，延迟接近固定超时时间 | TCP 重传、DNS/TLS 耗时、跨区调用 |

**第一步抓一批接近 800ms 的请求，沿同一条 trace 拆开：入口排队 → 应用处理 → 连接池等待 → 下游调用。** 同时对照异常前后的发布、QPS、并发和实例分布。

如果下游调用多了约 600ms，就沿那个下游查；如果应用收到请求前或获取连接前多了约 600ms，就查队列和池。这个拆分通常比继续盯机器平均 CPU 更快找到原因。
