**CPU 只有 30%，不代表接口没有瓶颈。**请求耗时包含计算、等待和排队；p99 上涨通常意味着少量请求遇到了较长的等待，平均 CPU 很容易掩盖它。

常见原因有：

| 原因 | 为什么 CPU 不高 | 重点看什么 |
|---|---|---|
| 下游变慢，如数据库、Redis、外部 RPC | 请求在等响应 | 链路追踪中哪个调用耗时增加 |
| 线程池、连接池耗尽 | 请求排队等资源 | 活跃数、等待队列、获取连接耗时 |
| 锁竞争或数据库锁等待 | 线程阻塞 | 线程栈、锁等待、长事务 |
| 磁盘或网络异常 | 等 I/O、重传或连接建立 | I/O 延迟、丢包、TCP 重传 |
| GC 暂停 | 少量请求被暂停拖长 | GC 日志、暂停时间与慢请求是否重合 |
| 局部 CPU 饱和或容器限流 | 整机平均值掩盖单核、单实例瓶颈 | 每核 CPU、各实例负载、CPU throttling |
| 超时重试或流量突增 | 个别请求多走一次调用，或进入队列 | 重试次数、QPS、并发数、流量分布 |

建议按这个顺序查：

1. **先确认影响范围。**看 p50、p95 是否也涨，以及是否集中在某个实例、某类参数或某个时间段。只有 p99 涨，更偏向偶发暂停、热点请求或局部拥堵。
2. **拆一条慢请求的时间线。**把 800ms 分成：入口排队、应用执行、获取连接、数据库/RPC、返回。重点找新增的约 600ms 落在哪里。
3. **检查等待资源。**优先看线程池和连接池队列、下游尾延迟、锁等待；再对照 GC、单核 CPU 和容器限流。

一个容易漏掉的反馈环是：**下游变慢 → 请求占用连接更久 → 连接池排队 → 接口进一步变慢**。这时 CPU 可能始终很低，盲目扩线程池还可能加重下游压力。
