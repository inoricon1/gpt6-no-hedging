**CPU 只有 30%，不代表接口没有瓶颈。** p99 从 200ms 涨到 800ms，说明最慢的那部分请求耗时增加了；它们可能在等待资源，也可能遇到短暂拥塞，而机器平均 CPU 看不出来。

常见原因有这些：

| 可能原因 | 典型表现 |
|---|---|
| **下游变慢**：数据库、Redis、外部 API | 请求大部分时间耗在某次调用上；慢 SQL、锁等待、缓存未命中都可能触发 |
| **连接池或线程池排队** | 执行本身很快，但获取连接、等待线程很久；CPU 仍然不高 |
| **锁竞争或并发限制** | 请求等待互斥锁、信号量或限流许可，只有少数任务在执行 |
| **磁盘或网络等待** | IO 延迟、网络丢包重传、DNS 或连接建立变慢 |
| **GC 或运行时停顿** | 延迟周期性出现尖峰，长时间平均 CPU 看起来正常 |
| **局部 CPU 瓶颈** | 单核、单个实例或容器已达到限制，被整机或集群平均值掩盖；也可能出现 CPU throttling |
| **少量请求走了慢路径** | 缓存失效、大请求、热点数据、重试，主要影响尾部延迟 |

我会按这个顺序排查：

1. **确认影响范围**：同时看 p50、p95、p99、QPS，以及各实例的数据。只有 p99 涨，优先查偶发停顿、慢路径和局部热点；整体都涨，优先查普遍的排队或下游变慢。
2. **找几条慢请求的 trace**：把耗时拆成入口排队、获取连接、下游调用、应用执行、响应发送。尤其要记录“等待连接”的时间，否则 trace 容易漏掉瓶颈。
3. **检查变化点和资源等待指标**：发布、流量突增、缓存命中率、连接池等待、线程池队列、数据库锁、GC pause、每核 CPU 和容器限额。

**最有价值的问题是：新增的耗时花在哪里，是在执行，还是在等待？** 在没有更多指标前，下游尾延迟和连接池／线程池排队值得优先检查，但仅凭 CPU 30% 还无法确定原因。
