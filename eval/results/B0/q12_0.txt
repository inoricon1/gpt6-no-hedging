**索引不保证查询更快。一个常见原因是：执行计划改用了索引，但“扫描索引 + 回表取数据”的实际开销，比原来的顺序扫描更大。** 你的情况需要看执行计划才能确认。

主要有这几种可能：

1. **条件命中了太多行，回表成本高。**  
   例如千万行表里，`WHERE status = '正常'` 命中了几百万行。普通索引扫描先找行的位置，再去表里取数据；如果这些行分散在大量数据页中，访问成本可能超过直接顺序读表。表大，并不意味着所有条件都适合索引。[官方扫描示例](https://www.postgresql.org/docs/current/using-explain.html)

2. **优化器低估了匹配行数，选错计划。**  
   统计信息过期、数据分布偏斜，或者多个条件之间有相关性，都可能影响估计。例如预计返回 100 行，实际返回 100 万行，原本看起来便宜的索引扫描就会很慢。更新统计信息是排查步骤之一。[官方索引诊断说明](https://www.postgresql.org/docs/current/indexes-examine.html)

3. **索引只解决了部分条件。**  
   查询还有其他筛选、排序或关联时，单列索引可能先取出大量候选行，再过滤、排序；也可能改变关联方式，造成大量重复索引访问。要看整个计划，而不只是有没有 `Index Scan`。[官方执行计划说明](https://www.postgresql.org/docs/current/using-explain.html)

4. **慢的原因来自测试环境。**  
   如果加索引前后计划相同，就需要比较缓存冷热、并发负载、I/O 等因素，不能仅凭“加完后变慢”判定因果。

建议先保存当前查询的实际执行计划：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;  -- 替换成原查询，使用相同参数
```

`ANALYZE` 会实际执行查询。重点看：

| 计划信息 | 要确认的问题 |
|---|---|
| `Seq Scan` / `Index Scan` / `Bitmap Heap Scan` | 是否改变了访问方式 |
| 估计 `rows` 与实际 `rows` | 是否严重低估了行数 |
| `Rows Removed by Filter` | 是否取出大量数据后才过滤 |
| `Buffers: shared hit/read` | 访问的数据页是否很多；`read` 不一定代表物理磁盘读取 |
| `loops` | 是否重复执行了大量扫描 |

保存计划后，可以执行 `ANALYZE 表名;`，再比较计划和耗时；测试尽量保持相同参数、相近负载，并重复几次。[官方 EXPLAIN 文档](https://www.postgresql.org/docs/current/using-explain.html)

把**原 SQL、索引定义和上述执行计划**贴出来，就能进一步判断是回表成本、估计错误，还是其他节点拖慢了查询。
