**报表任务是首要调查对象，但现有信息还不能确定是内存泄漏。** 固定时间发生、连续约 10 分钟增长，更符合“任务运行期间持续累积数据或积压”的特征；也可能是任务并发、正常峰值超过限额，或同一节点上的其他任务挤占内存。

下面是建议的排查顺序。尚未拿到日志和运行环境，因此原因排序是待验证的假设。

**1．先确认：是谁因为什么内存限制而退出**

三种情况的排查方向不同：

| 情况 | 应寻找的证据 | 排查重点 |
|---|---|---|
| 运行时内存耗尽 | Java `OutOfMemoryError`、Node.js heap limit、Python `MemoryError` 等完整错误 | 堆上限、对象保留、分配失败位置 |
| 容器触及内存限额，被内核杀死 | `OOMKilled`、容器限额、内核 OOM 记录 | 堆、堆外、子进程、文件缓存等总占用 |
| 节点内存耗尽或发生驱逐 | 节点 OOM 日志、`MemoryPressure`、`Evicted`、其他 Pod 同时异常 | 节点上的全部工作负载及资源配置 |

Kubernetes 中，内存限额由内核执行；内存不足导致的驱逐和容器 OOM 要分别确认。[Kubernetes 资源管理说明](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)

如果使用 Kubernetes，可以先执行这些只读命令，替换占位符：

```bash
kubectl describe pod <pod> -n <namespace>
kubectl logs <pod> -n <namespace> -c <container> --previous --timestamps
kubectl get pod <pod> -n <namespace> -o yaml
kubectl describe node <node>
```

重点查看退出原因、退出时间、容器名称、`requests/limits`、探针失败和事件。**退出码 137 只能说明 SIGKILL，不能单独证明 OOM。** Pod 已经被替换时，需要查历史日志和事件系统；新 Pod 的状态无法还原旧 Pod 的全部证据。

同时确认监控里的“60%→100%”到底是：

- 进程 RSS、运行时堆、容器 usage，还是 working set；
- 分母是容器 limit、request，还是节点总内存；
- 单个实例曲线，还是多个实例的聚合结果。

这些口径不清楚，后续容量判断很容易走偏。

**2．可能原因，按当前线索的调查优先级排序**

| 优先级 | 可能原因 | 典型机制 | 能验证它的证据 |
|---|---|---|---|
| 高 | 报表全量数据在内存中累积 | 分页读取后不断追加到总列表；ORM 保留对象；Excel 工作簿保留全部单元格 | 存活对象、列表长度或工作簿大小随已处理行数增长 |
| 高 | 生产速度超过消费速度 | 数据库读取快，文件写出或上传慢；异步队列没有上限 | 队列深度、待写字节数持续增加；下游吞吐低于读取吞吐 |
| 高 | 数据量或数据结构异常 | 查询范围扩大、漏过滤条件、JOIN 放大、某租户数据暴增、单行字段变大 | 失败日期的行数、字段大小、分组数量明显不同 |
| 中高 | 任务重叠或重复执行 | 多副本各自运行定时任务；上一轮未结束；超时重试时旧任务仍在执行 | 同一业务日期出现多个执行 ID，且运行时间重叠 |
| 中 | 合理业务峰值超过预算 | 在线服务原本占 60%，报表需要额外空间；转换、排序、序列化同时保留多份数据 | 对象最终能够释放，但单次任务峰值仍超过限额 |
| 中 | 报表触发真正的内存泄漏 | 全局缓存、监听器、闭包、线程本地变量或未关闭资源持续持有数据 | 相同任务重复执行后，存活对象基线逐轮升高，并找到引用链 |
| 中 | 堆外或其他进程增长 | 原生库、直接缓冲区、线程栈、PDF/浏览器子进程 | 堆较稳定，但 RSS、线程数或子进程占用增长 |
| 条件性 | 临时文件或节点上的其他任务 | 报表写到 tmpfs；备份、日志压缩等任务同时运行 | `shmem` 增长，或节点内存增长来自其他工作负载 |

如果报表每天都跑，**为什么一周只有三次失败**尤其值得查：这三天是否数据更多、启动前基线更高、下游更慢、并发更多，或者代码与配置发生变化。

**3．把三次故障和成功运行放到同一时间线上**

每次收集任务开始前约 30 分钟到重启后的数据，统一时区，按任务开始时间对齐。至少包含：

- **任务信息：**执行 ID、业务日期、实例、开始／结束时间、失败阶段、重试次数。
- **输入与进度：**查询参数、实际返回行数、已处理行数、批次大小、分组数量、输出字节数。
- **内存与运行时：**实际占用字节数、限额、堆使用量、GC 后存活量、GC 时间、线程／子进程数量。
- **依赖与在线流量：**数据库耗时、上传吞吐、队列深度、在线请求量及延迟。
- **变更：**发布版本、依赖版本、资源配置、报表规则和数据范围。

重点看：**内存开始上涨对应哪个处理阶段，而不是只看它是否发生在凌晨两点。**

可以计算两个辅助指标：

```text
增长速率 = 内存增量 / 时间
每行净增长 = 内存增量 / 同期已处理行数
```

例如，假设限额为 4 GiB，10 分钟从 60% 涨至 100%，平均净增长约为 **2.73 MiB/s**。再与读取行数、队列积压字节数或输出文件增长比较，可以帮助定位累积发生的位置。

这里测到的是**净增长**，并非总分配速率；线性曲线也可能掩盖采样间隔内的 GC 波动。

**4．拆开内存，找到增长属于哪一层**

不要只盯着总内存曲线。应同时看进程 RSS、运行时堆，以及容器中的其他内存。

Linux cgroup v2 可检查目标容器所属 cgroup 的：

```text
memory.current
memory.max
memory.events
memory.stat
```

其中 `memory.stat` 可以帮助区分匿名内存、文件页和共享内存；`memory.events` 提供 OOM 相关计数。需要记录故障前后的计数变化，并结合内核日志判断，单个 `oom_kill` 计数不能独立区分节点 OOM 和容器限额 OOM。[Linux cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)

根据结果分支：

- **堆内存及 GC 后存活量都增加：**查列表、Map、缓存、工作簿、队列和引用链。
- **堆稳定而 RSS 增加：**查原生分配、缓冲区、线程栈、内存映射和分配器碎片。
- **主进程稳定而容器占用增加：**查子进程、其他进程及临时文件。
- **节点占用增加而目标容器稳定：**查其他 Pod、备份和系统任务。

特别检查报表临时目录的挂载方式。Kubernetes 的 `emptyDir.medium: Memory` 使用 tmpfs，写入内容计入内存；把导出内容“落到临时文件”并不一定降低内存需求。[Kubernetes 临时存储说明](https://kubernetes.io/docs/concepts/storage/ephemeral-storage/)

注意这些指标存在重叠，不能把 RSS、堆和 cgroup 各项直接相加。

**5．用运行时工具定位具体对象或分配位置**

在有余量的隔离实例上，比较“任务前、增长中、任务完成后”的数据：

| 运行时 | 建议采集 | 重点观察 |
|---|---|---|
| Java | GC 日志、对象直方图／heap dump；已启用 NMT 时比较 native memory | retained size、GC Root 引用链、直接内存、线程 |
| Node.js | `heapUsed`、`rss`、`external`、`arrayBuffers`；堆快照或分配采样 | 数组、Map、闭包、Buffer、异步任务 |
| Python | 提前启用 `tracemalloc` 并比较快照，同时监控 RSS | 增长的分配调用栈；未被追踪的原生分配 |
| Go | heap／allocs profile、goroutine profile、运行时内存指标 | `inuse_space` 的增长、分配热点、阻塞 goroutine |

相关官方工具说明：[Java](https://docs.oracle.com/en/java/javase/25/troubleshoot/diagnostic-tools.html)、[Python](https://docs.python.org/3/library/tracemalloc.html)、[Go](https://go.dev/doc/diagnostics)。

**分配得多和保留得多是两回事。** 排查泄漏时，应优先寻找持续存活的对象及其持有者；任务结束后 RSS 没降，也可能是运行时保留内存或分配器碎片，不能直接认定泄漏。

快照采集要提前规划：Node.js 堆快照会暂停主线程，并可能显著增加内存占用，不能等线上实例快到 100% 时再抓。[Node.js 堆快照说明](https://nodejs.org/learn/diagnostics/memory/using-heap-snapshot)

**6．通过对照实验建立因果关系**

在隔离环境使用故障当天的数据和相同资源限制，每次只改变一个因素：

| 实验 | 结果如何解释 |
|---|---|
| 报表单独运行，再叠加相近在线负载 | 单独运行也失败，优先查报表自身；叠加后失败，查总预算和资源竞争 |
| 输入规模取 25%、50%、100% | 峰值随总行数增长，支持全量保留；随分组数量增长，支持聚合状态过大 |
| 固定数据，降低任务并发 | 峰值明显下降，支持并发放大，但仍需验证单任务占用 |
| 固定数据，限制队列容量并启用背压 | 曲线从持续增长变成平台，支持积压机制 |
| 跳过导出／上传，仅做读取和计算 | 判断问题发生在读取、聚合、文件生成还是上传 |
| 同一进程连续运行相同任务多次 | 存活量基线逐轮升高，支持泄漏；稳定高峰更符合容量不足 |

扩大内存后任务完成，只能证明它跨过了原来的限制，不能单独证明实现没有泄漏。

如果采用 Kubernetes CronJob，可检查 `concurrencyPolicy`；`Forbid` 只约束同一个 CronJob 创建的任务，不能解决多个 CronJob 或应用内定时器的重复执行。业务任务仍需去重和幂等。[CronJob 官方说明](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/)

**7．止血、修复和验收**

下一次凌晨任务前，建议优先完成：

1. 保存三次故障的历史日志、退出信息和监控原始数据。
2. 如果报表与在线请求共用进程，把报表隔离到独立 worker／Job，并限制任务并发和重试。
3. 对输入规模、队列深度、运行时间设置明确上限，避免失控增长。
4. 经节点容量确认后，可临时增加内存余量；同时保留增长监控和诊断数据。

针对根因修复：

- **全量累积：**改为游标／分批读取、逐批处理、流式写出，及时释放批次引用。
- **队列积压：**使用有界队列和背压，让读取速度受下游吞吐约束。
- **重复执行：**增加任务唯一键、互斥机制、合理租约和幂等输出。
- **对象泄漏：**修复持有引用的位置，明确缓存和资源的生命周期。
- **容量不足：**按实测峰值配置预算，覆盖在线业务、报表并发、运行时开销、堆外及临时文件，并预留余量。

验收不能只看“一晚没重启”。应验证最大合理数据量、下游变慢、任务重试和多次重复运行：**峰值有界，队列有界，存活对象基线不持续抬升，报表结果完整，在线服务延迟符合要求。** 告警同时覆盖内存占比、增长速率、任务并发及队列深度，才能在下一次到达限额前采取措施。
