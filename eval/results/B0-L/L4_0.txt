**报表任务是最值得优先验证的触发因素，首先查“处理过程中不断保留数据”和“生产快、消费慢导致积压”。但目前还不能据此认定内存泄漏。** 正常报表的峰值超过限额、任务重复执行、堆外内存增长，甚至同机其他任务耗尽内存，都可能造成类似现象。

建议按照“确认 OOM 类型 → 对齐时间线 → 找出增长的内存 → 定位报表阶段 → 对照复现”的顺序排查。下面的命令以 Linux／Kubernetes 为例，其他部署方式按同样思路取证。

**1. 先确认是谁因为什么被重启。**

首先弄清监控的“60% → 100%”到底是什么：应用堆占用、进程 RSS、容器内存，还是整台机器内存？分母是堆上限、容器 limit，还是物理内存？保留绝对字节数、原始采样和单实例曲线，避免聚合或平滑掩盖变化。

需要区分三种情况：

| 类型 | 主要证据 | 排查方向 |
|---|---|---|
| 应用运行时 OOM | Java `OutOfMemoryError`、Node.js heap out of memory 等原始日志 | 对应内存池的上限、对象存活量和分配来源 |
| 容器内存限额触发 OOM | 容器终止状态、cgroup 事件、内核日志 | 容器内全部内存，包括堆外、子进程和文件相关内存 |
| 宿主机 OOM／节点内存压力 | 内核 OOM 日志、节点可用内存、其他进程用量、驱逐事件 | 同机竞争；被杀的服务也可能只是受害者 |

Kubernetes 下先取：

```bash
kubectl describe pod <pod> -n <namespace>
kubectl logs <pod> -n <namespace> -c <container> --previous --timestamps
kubectl get pod <pod> -n <namespace> -o yaml
kubectl describe node <node>
```

检查 `lastState.terminated`、时间、reason、exitCode，以及实际生效的资源配置。**137 单独只能说明收到 SIGKILL，不能独立证明 OOM。** 容器限额和节点压力驱逐也应分别核对。[Kubernetes 资源管理说明](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)、[节点压力驱逐说明](https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/)

在对应节点上查看故障窗口：

```bash
journalctl -k --since "<开始时间>" --until "<结束时间>"
```

查找 `Out of memory`、`Killed process`、`Memory cgroup out of memory`，确认被杀 PID、进程名和所属 cgroup。历史 Pod、事件和前一实例日志可能已经被清理，需要从集中日志系统补齐。

**2. 对齐三次故障，并与成功运行比较。**

以每次任务启动为零点，整理启动前 30 分钟到结束／重启后 30 分钟的数据，统一时区。至少记录：

- 报表任务的 `run_id`、实例、查询条件、数据范围、开始／结束时间、当前阶段。
- 输入行数、累计处理行数、输出字节数、并发数、待处理队列长度、重试次数。
- 内存绝对值、堆使用量、GC 后存活量、CPU、GC 耗时、CPU throttling。
- 在线请求并发、延迟，以及数据库、存储、上传接口的延迟。
- 同时段其他任务：备份、ETL、日志压缩、缓存刷新、索引构建。

**如果报表每天执行，为什么过去一周只有三次失败，是很有价值的线索。** 对比失败日与成功日：数据量是否更多、某个租户是否异常、数据库是否变慢、是否有重试或重叠任务、版本和资源配置是否变化。

重点检查内存开始上涨是在“任务启动后”，还是“读取／聚合／导出／上传”某个阶段开始后。

**3. 按以下优先级验证原因。**

这个顺序是根据现象安排的排查优先级，不是已经确认的结论。

| 可能原因 | 典型机制 | 如何验证 |
|---|---|---|
| **数据累计留在内存** | 全量查询、分页结果持续追加到总列表；ORM 会话持续跟踪对象 | 存活对象数量随累计行数增加；持有者是集合、会话或任务上下文 |
| **报表生成器持续缓存** | Excel 单元格／样式、PDF 页面、整份 CSV 字符串、内存压缩包一直保留 | 查询结束后仍增长；主要对象来自报表库或大字节数组 |
| **队列积压、缺少背压** | 读取比渲染／上传快，未完成任务、结果或缓冲区持续堆积 | 队列长度与内存同步增长；下游变慢时斜率增大 |
| **重复执行或并发放大** | 多副本各跑一次；租户并行；超时重试时旧任务仍在执行 | 同一报表出现多个活跃执行；降并发后峰值明显下降 |
| **单次正常峰值超过预算** | 数据变多，或原始数据、对象、序列化结果同时存在 | 同规模数据稳定复现；结束后存活对象回落，重复运行不持续累积 |
| **对象或资源未释放** | 缓存、全局引用、监听器、ThreadLocal、未关闭资源持续持有数据 | 同一进程多次运行后，任务结束并回收后的基线不断抬升 |
| **堆外／原生／子进程增长** | Buffer、直接内存、原生库、线程栈、浏览器／PDF 子进程 | RSS／容器内存上涨，而托管堆增长不足以解释 |
| **临时文件占用内存** | 报表写到 tmpfs、内存型 `emptyDir`；文件页和脏页增长 | 文件用量、cgroup 文件相关指标随报表输出增长 |
| **GC 或资源竞争放大问题** | 高分配速率、CPU 限流拖慢回收；共享数据库变慢使请求堆积 | GC、CPU 限流、在线在途请求与内存增长同时恶化 |

要特别检查代码里的这些模式：`fetchall()`、`collect()`、分页后 `append/extend`、一次创建所有异步任务、全量排序／分组、整份内容转字符串、生成文件后再完整读入内存上传。

**分页只限制单次查询大小；如果结果最后仍汇总到一个集合，整体内存仍可能随总数据量增长。**

另外，写到“临时目录”不一定意味着使用磁盘。Kubernetes 的内存型 `emptyDir` 会计入内存用量。[官方说明](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)

**4. 在下一次运行前，把增长归属到具体内存。**

任务窗口内建议以 10～15 秒粒度采集，并同步记录报表进度：

| 观察结果 | 下一步 |
|---|---|
| 堆使用量和 GC 后存活量持续增长 | 查哪些对象增加、谁仍引用它们 |
| 分配量很高，但 GC 后存活量基本稳定 | 查临时对象、瞬时峰值和回收能力 |
| RSS 增长，堆较稳定 | 查原生分配、直接内存、线程、映射和分配器保留 |
| 容器内存增长，主进程 RSS 较稳定 | 查子进程、tmpfs、文件页和内核相关内存 |
| 节点内存下降，服务自身基本稳定 | 查同机其他任务和进程 |

Linux 下可查看 `/proc/<pid>/status`、`smaps_rollup` 和进程树。cgroup v2 下查看**目标容器实际所属路径**的 `memory.current`、`memory.max`、`memory.events`、`memory.stat`，比较 `anon`、`file`、`shmem` 等变化及 OOM 事件计数增量。`shmem` 等字段存在包含关系，不要把所有字段直接相加。[Linux cgroup v2 文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

按语言选择工具：

- **Java**：GC 日志、JFR、对象直方图／heap dump；分析 retained size 和到 GC Root 的引用链。堆解释不了 RSS 时用 NMT，但它不覆盖全部第三方原生分配。OS 直接杀进程时，`HeapDumpOnOutOfMemoryError` 不保证留下 dump。[Oracle 排查说明](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshooting-memory-leaks.html)
- **Go**：对比任务前、中、后的 heap profile；区分 `inuse_space` 与累计 `alloc_space`，同时看 goroutine 是否积压。[pprof 文档](https://pkg.go.dev/runtime/pprof)
- **Python**：提前开启 `tracemalloc`，比较阶段快照；若增长与 RSS 对不上，再查原生扩展和子进程。[tracemalloc 文档](https://docs.python.org/3/library/tracemalloc.html)
- **Node.js**：同时看 `heapUsed`、`rss`、`external`、`arrayBuffers`，用快照比较对象持有关系。快照会暂停主线程，还可能显著增加内存，应在隔离实例且有余量时采集。[Node.js 快照说明](https://nodejs.org/en/learn/diagnostics/memory/using-heap-snapshot)

**不要仅因任务结束后 RSS 没立即下降就判定泄漏。** 运行时或分配器可能保留已释放空间；应结合存活对象、重复运行后的基线和内存是否被后续任务复用判断。

**5. 用对照实验验证因果，避免只凭时间相关性下结论。**

在隔离 worker 或测试环境里，使用失败日相同的数据范围、版本和资源上限，逐项实验，每次只改变一个变量：

| 实验 | 能回答的问题 |
|---|---|
| 只读取并计数，不生成报表 | 查询驱动／ORM 是否已经持有大量数据 |
| 使用固定输入，只生成报表 | 报表库是否是主要增长来源 |
| 分别测读取、聚合、导出、上传 | 哪个阶段开始保留数据或积压 |
| 数据量按 25%、50%、100% 放大 | 峰值是否随总行数／分组数增长 |
| 并发降到 1 | 并发和重复执行是否放大内存 |
| 人为放慢上传／下游 | 是否缺少背压，队列是否无界 |
| 同一进程连续运行多次 | 结束后的存活基线是否持续抬升 |
| 暂停报表，或在其他时刻单独运行 | 故障是否跟随任务，而不是固定凌晨发生 |

“停掉报表后不再 OOM”支持报表参与了故障，但仍需定位机制。例如报表可能抢占数据库连接，导致在线请求堆积，而不是自身持有了全部新增内存。

若监控分母确实是固定限额 `L`，你给出的曲线对应平均净增长约：

```text
增长速率 ≈ (100% - 60%) × L / 10 分钟
         ≈ 0.04 × L / 分钟
```

再除以每分钟处理行数，可以估算“每处理一行净保留多少字节”。这个值若比较稳定，值得优先检查按行累计的数据结构。它是**净增长估算**，不是对象分配速率；先确认曲线没有被平滑。

**6. 先保护在线服务，再修复已验证的机制。**

建议今晚运行前先保存现有证据，并按业务时效要求采取措施：

- 将报表放到独立进程／容器，设置独立资源预算；同时限制它对共享数据库和存储的并发。
- 全局限制同一报表同时执行的数量，设置超时、取消和有界重试，确保取消后旧任务真的停止。
- 限制批次大小、任务队列和上传缓冲区，给下游增加背压。
- 若短期扩容，先确认节点容量，并给堆外、子进程和文件相关内存留空间。
- 使用增长速率和预计耗尽时间提前告警，留出取消或降载的时间。

如果使用 Kubernetes CronJob，`concurrencyPolicy: Forbid` 只限制**同一个 CronJob**创建的 Job 重叠；多个 CronJob、手动补跑、应用内部调度仍需去重和互斥。[CronJob 文档](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/)

最终修复应对应证据：累计集合改流式处理；队列积压改有界队列和背压；聚合改数据库预聚合或落盘；对象泄漏修引用生命周期；正常峰值超限则重新制定容量预算。

**7. 用明确标准确认修复完成。**

至少验证失败日数据规模、合理增长后的规模、慢下游、重试，以及同进程重复运行。验收应同时满足：

- 报表内容完整、正确，没有漏行或重复。
- 峰值在内存预算内，留有明确余量。
- 队列、并发和缓冲区都有上限。
- 多次运行后的存活内存基线稳定。
- 在线服务延迟、错误率和共享数据库负载符合要求。
- 覆盖原故障条件的连续运行通过。

目前最值得优先拿到的四项证据是：**OOM 原始终止记录、内存指标名称与限额、报表各阶段的进度和并发、失败日与成功日的数据量差异。** 它们能最快决定下一步该查对象持有、队列积压，还是容器／节点资源。
