**CPU 只有 30%，说明整体平均占用较低；定位瓶颈还需要排队、等待和局部资源指标。** 请求耗时包括执行时间、排队时间和等待时间；后两者很长时，CPU 仍然可能很低。p99 从 200ms 涨到 800ms，首先要查慢请求多出来的约 600ms 花在哪里。

常见原因有这些：

| 可能原因 | 为什么 CPU 不高 | 重点检查 |
|---|---|---|
| **下游变慢**：数据库、缓存、第三方接口 | 线程在等响应 | 下游调用 p99、慢 SQL、数据库锁等待、缓存命中率 |
| **连接池或线程池耗尽** | 请求排队等连接或工作线程 | 获取连接耗时、活跃连接数、等待数、任务队列长度 |
| **锁竞争或并发限制** | 线程阻塞等待 | 线程栈、锁等待时间、信号量等待 |
| **磁盘或网络异常** | 等 I/O、重传或超时 | 磁盘延迟、TCP 重传、丢包、连接建立耗时 |
| **GC 或运行时停顿** | 短暂暂停被平均 CPU 掩盖 | GC 暂停时长、分配速率、事件循环延迟 |
| **局部 CPU 瓶颈** | 整机平均值掩盖单核打满，或容器被限额 | 每核利用率、进程 CPU、容器 CPU throttling |
| **流量或请求结构变化** | 突发流量产生队列，少量重请求拉高尾延迟 | QPS、并发数、请求大小、热点 key、重试次数 |

**只看 p99，还要区分是整体变慢还是尾部变慢：**

- **p50 也明显上涨**：优先查公共依赖、普遍排队或整体资源瓶颈。
- **p50 基本不变，只有 p99 上涨**：优先查少量慢 SQL、热点锁、GC、超时重试，以及某个异常实例。

我会按这个顺序定位：

1. **确认统计口径**：延迟是在网关还是应用内测量？CPU 是整机、容器还是进程？按实例拆开，避免平均值掩盖问题。
2. **对比变更和流量**：延迟上涨是否与发布、配置变化、QPS 增长、缓存失效同时发生。
3. **抓慢请求的链路追踪**：拆出入口排队、连接池等待、数据库/外部调用、应用执行的耗时，和正常请求比较。连接池等待可能需要单独埋点。
4. **缺少 trace 时抓线程栈**：在慢的时刻连续采几次，看线程是在等连接、锁、网络，还是持续执行某段代码。

关键判断是：**请求在哪里等待，以及谁限制了并发。** 整机 CPU 较低时，容量问题仍需结合局部资源和队列指标判断；先找到新增的等待时间，再判断扩容是否有效。
