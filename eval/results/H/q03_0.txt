**CPU 只有 30%，说明机器平均 CPU 负载较低，瓶颈位置还需结合等待和排队耗时判断。** 请求可能大部分时间在等待；而 p99 反映的是最慢约 1% 的请求，少量慢请求就能把它从 200ms 拉到 800ms。

常见原因有这些：

| 可能原因 | 为什么 CPU 不高 | 优先看什么 |
|---|---|---|
| **下游变慢**：数据库、Redis、外部接口、磁盘 | 请求在等 I/O | 慢请求的调用链、下游 p99、慢 SQL |
| **连接池或线程池耗尽** | 请求排队等待可用连接或线程 | 活跃连接数、等待队列长度、获取连接耗时 |
| **锁竞争或串行瓶颈** | 大量线程阻塞，只有少数线程运行 | 线程栈、锁等待、数据库锁 |
| **流量或并发增加** | 下游或池容量先达到上限 | QPS、在途请求数、队列等待时间 |
| **超时、重试或网络抖动** | 等超时、退避、重传期间几乎不耗 CPU | 重试次数、超时分布、TCP 重传、连接建立耗时 |
| **GC、单核满载或容器 CPU 限流** | 整机平均 CPU 掩盖局部或短时瓶颈 | GC 暂停、每核 CPU、容器 throttling |
| **少量特殊请求变慢** | 缓存未命中、大数据查询等只影响尾部 | 慢请求的数据量、缓存命中情况、所在实例 |

我会按下面顺序排查：

1. **确认影响范围**：p50、p95 是否也上涨？是否集中在某个实例、某类参数，或某次发布之后？
2. **找几条 800ms 的慢请求，与正常请求对比调用链**：新增的 600ms 花在下游调用、获取连接、排队，还是应用内部？
3. **优先检查等待指标**：连接池等待、线程池队列、数据库锁、下游 p99；随后看 GC、每核 CPU 和容器限流。

一个容易漏掉的点：**请求进入业务代码前的排队时间需要单独核对**。如果客户端看到 800ms，但应用内 trace 只有 200ms，就要检查网关、负载均衡和服务接入队列。

这两个指标提供了排查方向，确定原因还需耗时分解。优先怀疑**下游等待和池资源排队**，扩容决策应结合实际瓶颈和资源饱和指标。
